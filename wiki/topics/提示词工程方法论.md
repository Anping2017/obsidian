# 提示词工程方法论

## 概述

[[提示词工程]] 不是写一句"聪明话",而是一整套系统化的工程实践:从结构化 prompt 设计、模式选择,到效果评估、版本管理、团队协作,再到与 [[RAG]]、[[函数调用]] 等能力组合。本主题梳理一套从初学到落地的完整方法论。

## 多角度分析

### 设计原则

- **清晰性**:指令明确,避免歧义
- **具体性**:用具体例子和约束代替抽象形容词
- **结构化**:用标题、列表组织 prompt
- **正向表达**:写要做什么,而非禁止做什么
- **关键信息位置**:重要约束放开头与结尾

### 结构要素(RTCF / RTCFE)

| 要素 | 作用 |
|---|---|
| Role | 设定身份和视角(参见 [[角色提示]]) |
| Task | 明确任务目标和成功标准 |
| Context | 提供背景、参考材料、约束 |
| Format | 输出格式与长度要求(参见 [[结构化输出]]) |
| Examples | 示例([[少样本提示]]) |

### 主要模式

- [[零样本提示]]:简单任务、模型已会的任务
- [[少样本提示]]:格式严格、风格特定、难以言传的任务
- [[思维链]]:复杂推理、多步逻辑
- [[角色提示]]:专业咨询、风格控制
- 提示词链:把复杂任务拆成多步 prompt 串联
- ReAct:推理 + 工具调用交替,见 [[AI Agent]]
- Self-Consistency:多次采样投票,提高可靠性

### 迭代优化流程

1. 明确任务与成功指标
2. 起一个 baseline prompt
3. 用代表性输入测试,观察失败模式
4. 针对失败模式逐项修补:加示例、加约束、改格式
5. 建立测试集,后续修改用 A/B 验证
6. 监控线上效果,偏离时回滚或迭代

### 工程化实践

- **版本管理**:把 prompt 当代码用 Git 管理,每次改动记录原因
- **测试集**:维护一组(输入, 期望输出)用于回归
- **评估管线**:自动化跑测试集,产出指标(参见 [[模型评估]])
- **多模型对比**:同 prompt 在不同模型上效果差异巨大,需独立调优
- **环境隔离**:开发、测试、生产 prompt 分离
- **协作规范**:命名约定、共享模板库、Code Review

### 安全维度

- [[提示注入]] 是头号威胁,设计时必须假设外部输入恶意
- 系统指令与用户输入用明确分隔符或独立通道传输
- 关键操作(资金、删除、外发)必须二次确认
- 测试集中包含红队样本

### 何时升级到微调或 RAG

| 信号 | 应对 |
|---|---|
| prompt 越加越长仍不稳定 | 考虑 [[预训练与微调]] / [[LoRA]] |
| 知识更新快、私有知识 | 用 [[RAG]] |
| 严格 schema、复杂工具链 | [[函数调用]] / [[MCP协议]] |
| 多步推理频繁出错 | 拆分为 [[AI Agent]] 多步流程 |

## 结论

提示词工程是把 [[大语言模型]] 这种"概率黑盒"变成可控生产组件的工程学。**核心心法**:接受模型不完美,用结构、示例、约束、评估、迭代闭环去管理风险。**最常见错误**:把 prompt 当一次性试错,缺少测试集和版本控制,导致每次模型升级或细节修改都要重新摸索。**最大投资回报来源**:建立可重复的评估闭环,这能让 prompt 改动从"赌博"变成"工程"。
