# 系统设计原则

## 概述

软件系统从一个函数到全球性分布式服务,尺度跨越 10⁹ 倍,但**好设计的原则惊人地一致**:分离关注点、最小化共享、定义清晰边界、让失败可见、为变化保留余地。

本主题汇总从代码层([[设计原则SOLID]])到架构层(微服务、容错、可观察)的设计原则,串起"为什么这样设计"的连贯逻辑。

## 多角度分析

### 代码层:[[设计原则SOLID]]

- **单一职责**:一类一事
- **开闭**:对扩展开放、对修改关闭
- **里氏替换**:子类可替父类
- **接口隔离**:细粒度接口
- **依赖倒置**:依赖抽象不依赖实现

支撑:[[设计模式]]是它们的具体落地。
辅助原则:DRY、KISS、YAGNI、迪米特法则、组合优于继承。

### 模块层

- **高内聚、低耦合**:模块内部紧密相关、模块间通信极少
- **稳定依赖**:依赖应指向更稳定的方向
- **接口清晰**:契约明确,内部实现可换
- **错误边界**:把异常封装在模块内,对外提供统一错误码或类型

### 服务层(进程内 → 跨进程)

- **每服务单一职责**(对应 SRP 在系统层)
- **数据私有**:每服务一数据库,通过 API 暴露能力
- **API 优先(API-First)**:先定接口再写实现
- **向后兼容**:版本化、契约测试
- **幂等设计**:重试不重复副作用

### 分布式系统的关键原则

#### 容错:为失败设计(Design for Failure)

- **任何东西都会失败**(机器、网络、磁盘、依赖)
- **超时(Timeout)**:不允许"等到天荒地老"
- **重试 + 退避(Backoff)**:指数退避 + 抖动避免雪崩
- **熔断(Circuit Breaker)**:下游故障自动断开,避免级联崩溃
- **降级(Fallback / Graceful Degradation)**:核心保住,边缘降级
- **隔离(Bulkhead)**:故障域隔离,一处坏不拖全局
- **舱壁与限流**:保护自己不被压垮

#### 可扩展性

- **水平扩展优先**:加机器而不是换大机器
- **无状态化**:状态外置到[[缓存]] / [[关系型数据库|DB]] / [[消息队列|MQ]],应用进程随起随停
- **分区(Sharding)**:用[[一致性Hash]]或范围分区
- **读写分离 + [[缓存]]**:读放大、写吞吐量
- **异步化**:能异步不同步,用[[消息队列]]解耦

#### 一致性 vs 可用性

- **CAP 定理**:分区时只能在 C 和 A 间二选一
- **PACELC**:无分区时还需在延迟和一致性间选
- **强一致 vs 最终一致**:[[ACID事务]] vs BASE
- **共识算法**:Paxos / Raft / ZAB,用于元数据/选主

#### 数据一致性策略

- **2PC、3PC**:跨服务原子事务,但阻塞、慢
- **Saga**:补偿事务序列
- **TCC**:Try-Confirm-Cancel
- **事件溯源(Event Sourcing) + CQRS**:读写模型分离
- **Outbox 模式**:本地事务 + 事件表保证消息发出

### 可观察性(Observability)

> "你不能调试看不见的系统。"

三大支柱:
- **Logging**:结构化日志(JSON),关联 trace ID
- **Metrics**:Prometheus + Grafana,服务黄金指标(RED/USE)
- **Tracing**:OpenTelemetry,分布式调用链

进一步:
- **健康检查**:liveness、readiness、startup
- **告警与 SLO**:基于错误预算的告警
- **混沌工程**:Netflix Chaos Monkey,主动注入故障验证韧性

### 安全:纵深防御

- **零信任**:不假设网络位置即可信任
- **最小权限**:每身份只授予必需权限
- **多层防御**:WAF + 应用校验 + DB 权限 + 加密
- **加密分层**:传输加密(TLS)+ 存储加密(at rest)+ 敏感字段加密(application-level)
- 见[[Web安全]]

### 性能与成本

- **测量胜于猜测**:Profile,不要凭直觉优化
- **大 O 优于常数优化**:先把[[复杂度分析|复杂度]]降下来再优化常数
- **[[缓存]]是万能解**(几乎):多级缓存架构
- **延迟敏感链路同步,吞吐敏感链路异步**
- **成本意识**:云时代每个 CPU/内存/IO 都对应账单

### 可演化性

- **避免过早抽象**:先做出来再重构
- **YAGNI**:你不需要它(直到确实需要)
- **版本化 API**
- **渐进迁移**:Strangler Fig 模式逐步替换老系统
- **Feature Flag**:功能开关解耦发布与上线

## 结论

### 核心张力(永恒)

- **简单 vs 灵活**:抽象越多,灵活但门槛高
- **强一致 vs 高可用**:CAP 二选一
- **吞吐 vs 延迟**:批处理 vs 单请求
- **去中心 vs 易管控**:微服务自治 vs 集中管理
- **创新 vs 稳定**:新框架收益 vs 风险

### 反原则与反模式

- **过度工程**:为想象需求建复杂抽象
- **金锤子**:一种工具锤所有问题
- **分布式单体**:服务拆开但部署、测试、发布耦合
- **大爆炸重写**:一次性替换全部老系统(成功率极低)
- **测试覆盖率 KPI**:刷数字不提质量
- **盲目追新**:用最新技术不评估成熟度

### 学习与实践路径

1. 单体 → 模块化单体 → 服务拆分,渐进
2. 看几本经典:Clean Code、Clean Architecture、Designing Data-Intensive Applications、SRE
3. 读真实系统案例:Netflix、Uber、Stripe、AWS Builders' Library
4. 自己经历过 P0 故障是不可替代的成长
