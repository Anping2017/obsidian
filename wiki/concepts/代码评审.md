# 代码评审

## 定义

**代码评审(Code Review)** 是变更合并前由其他开发者(同事 / Tech Lead / 多人)阅读、提问、批注、提出修改意见的过程。现代实践多围绕 Pull Request / Merge Request 工具(GitHub、GitLab、Gerrit)展开,既是质量门禁也是知识传播仪式。

## 核心要点

- **目的**
  - 发现 Bug、安全风险、性能隐患。
  - 保持架构与编码风格一致(团队 [[整洁代码]] 共识)。
  - 知识扩散:让多人理解新代码,降低 BUS 因子。
  - 设计反馈:在落地前发现更好方案。
  - 教练学徒:资深与新手相互学习。
- **变更要小**
  - 理想 200-400 行;超过 1000 行评审注意力骤降。
  - 大变更应拆成可独立评审的串联 PR。
  - 每个 PR 一个意图 —— 重构、新功能、bug 修复不混合。
- **评审清单**
  - **正确性**:实现是否符合需求,边界与并发是否考虑。
  - **可读性**:命名、结构、注释是否清晰;读者能否快速理解。
  - **可测性 / 测试覆盖**:有无测试,关键路径是否覆盖。
  - **设计**:是否遵循 [[设计原则SOLID]];模块边界是否合理。
  - **安全**:输入校验、注入、权限校验、敏感数据处理。
  - **性能**:N+1 查询、循环内 IO、未释放资源。
  - **文档**:API 注释、CHANGELOG、迁移说明。
- **沟通规范**
  - 评论"代码"不评论"人":用"这段代码"而非"你"。
  - 区分意见层级:**must / should / nit / question**;nit 与 question 不阻塞合并。
  - 给出建议或例子,不只指出问题。
  - 异步与同步结合:大设计问题约同步会议而非长留言。
- **作者侧礼仪**
  - PR 描述包含动机、设计、测试方法、风险。
  - 自审一遍再请别人看。
  - 回复每条评论:接受、解释或讨论;改完后留 "done" 或链接到 commit。
- **工具与自动化**
  - **静态分析**(Lint、SonarQube、CodeQL)、格式化(Prettier、gofmt、Black)在 CI 跑,把风格争论自动化。
  - **覆盖率报告**、安全扫描挂在 PR 状态检查。
  - **CODEOWNERS** 自动分配评审人。

## 关系

- 是 [[CI_CD流水线]] 与 [[GitFlow与TrunkBased]] 工作流的核心节点。
- [[整洁代码]]、[[设计原则SOLID]]、[[设计模式]]、[[Web安全]] 都在评审清单中。
- 与 [[TDD测试驱动开发]] 配合——有测试的 PR 评审更聚焦设计。
- 与 [[技术债管理]]:在评审中标记为"已知债",记入 backlog。
- 工具如 GitHub Review、Gerrit、Phabricator 嵌入团队工作流。
