# 数据库锁机制

## 定义

**锁(Lock)** 是数据库为协调并发事务访问共享数据而引入的同步机制。当一个事务获取某资源的锁后,其他事务对该资源的冲突访问被阻塞或失败。锁是 [[ACID事务]] 隔离性的传统实现,与 [[MVCC]] 互补使用。

## 核心要点

- **按访问模式分类**
  - **共享锁(S 锁,Read Lock)**:多个事务可同时持有,允许并发读
  - **排他锁(X 锁,Write Lock)**:同一时刻仅一个事务持有,阻塞其他读写
  - **更新锁(U 锁)**:SQL Server 的特殊锁,介于 S 和 X 之间,防止死锁(SELECT ... FOR UPDATE)
- **按粒度分类**(InnoDB 视角)
  - **行锁(Row Lock)**:锁单行,并发最好,管理成本最高
  - **间隙锁(Gap Lock)**:锁住索引记录之间的"间隙",防止 INSERT 到该范围,实现 RR 级别下的幻读防护
  - **Next-Key Lock**:行锁 + 间隙锁,InnoDB RR 级别的默认锁
  - **表锁(Table Lock)**:锁整表,DDL 或 LOCK TABLES 时使用
  - **元数据锁(MDL)**:DDL 与 DML 互斥,保证表结构一致
- **意向锁(Intention Lock)**
  - **IS / IX**:表级标志,表示"表内某行有 S/X 锁"
  - 作用:申请表锁前快速判断是否有行锁冲突,避免遍历所有行
- **加锁时机**
  - **悲观锁**:操作前先加锁(SELECT...FOR UPDATE / LOCK IN SHARE MODE),适合冲突高的场景
  - **乐观锁**:不加锁,提交时检查版本号(WHERE version=?),冲突低的场景性能好
- **死锁(Deadlock)**
  - 两个或多个事务相互等待对方持有的锁,形成环
  - **检测**:InnoDB 用等待图(wait-for graph)定时检测,发现环则回滚代价最小的事务
  - **预防**:固定加锁顺序、缩短事务、降低隔离级别、合理建索引(锁粒度更细)
- **锁等待与超时**
  - innodb_lock_wait_timeout(默认 50s):等不到锁的事务报错
  - 长锁等待是慢查询、应用卡顿、超时雪崩的常见根因
- **分布式锁**
  - 单机锁不够用时,需跨节点协调
  - 实现:Redis(SET NX EX + Redlock)、ZooKeeper(临时顺序节点)、etcd(Lease + Compare-And-Swap)
  - 见 [[分布式锁]]
- **乐观并发控制(OCC)**
  - 不加锁,事务读取时记录版本/时间戳,提交时检查是否被改过,改过则重试
  - 适合 [[缓存]] + 数据库的扣减库存、Git 合并冲突等场景

## 和其他概念的关系

锁与 [[MVCC]] 是数据库并发控制的两种思路:MVCC 让读无锁、写不阻塞读,但写写冲突仍需锁。现代数据库通常 MVCC + 行锁组合。

锁直接决定 [[事务隔离级别]] 的实现:Serializable 用范围锁/谓词锁,RR 用 Next-Key Lock,RC 只用行锁。

[[关系型数据库]] 的锁机制比 [[NoSQL数据库]] 复杂得多;在 [[分布式事务]](2PC/TCC/Saga)中,锁会跨节点持有,引发雪崩风险。

[[慢查询优化]] 中,死锁日志和锁等待是排查热点。在 [[微服务]] 架构下,数据库锁应尽量短小,长事务跨服务等待是性能杀手。

[[分布式锁]] 是单机锁在跨节点场景的延伸,需要解决脑裂、续约、公平性等额外问题。
