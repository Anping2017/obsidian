# 查询优化器

## 定义

**查询优化器(Query Optimizer)** 是数据库管理系统中负责把声明式 SQL 转换为最高效执行计划的组件。它从无数等价计划中(扫描方式、连接顺序、JOIN 算法、聚合方式等)选择代价最低的一个,是关系数据库性能的核心技术。

## 核心要点

- **SQL 执行流水线**
  - 1. **解析(Parse)**:词法 + 语法分析,生成抽象语法树
  - 2. **验证(Validate)**:检查表/列存在、权限、类型
  - 3. **重写(Rewrite)**:视图展开、子查询提升、谓词下推等等价变换
  - 4. **优化(Optimize)**:生成多个物理计划,选最优
  - 5. **执行(Execute)**:按计划运行
- **两类优化器**
  - **RBO(Rule-Based Optimizer,基于规则)**:按预定义优先级选索引,简单但不能反映数据分布;Oracle 早期、MySQL 8 之前
  - **CBO(Cost-Based Optimizer,基于代价)**:估算每种计划的 IO/CPU 代价,选最小;现代主流
- **代价模型**
  - **统计信息**:表行数、列基数、值分布直方图、索引高度
  - **代价公式**:cost = α × CPU + β × IO + γ × 网络
  - 统计信息过期(ANALYZE 没跑)是 CBO 选错计划的常见原因
- **关键决策**
  - **访问路径**:全表扫描 vs 索引扫描 vs 索引覆盖扫描
    - 索引选择性低(如 sex='M'选 50% 行)时,全表扫描反而更快
  - **JOIN 顺序**:N 表 JOIN 有 N! 种顺序,实际通过动态规划或贪心搜索
    - 小表驱动大表通常是好策略
  - **JOIN 算法**:[[SQL高级特性]] 详解
    - **Nested Loop**:小表 × 有索引的大表
    - **Hash Join**:大表 × 大表 + 内存够
    - **Sort-Merge Join**:已排序或需要排序输出
  - **聚合方式**:Hash Aggregate vs Sort Aggregate
- **执行计划查看**
  - MySQL:EXPLAIN / EXPLAIN ANALYZE
  - PostgreSQL:EXPLAIN ANALYZE BUFFERS
  - Oracle:SET AUTOTRACE / DBMS_XPLAN
  - 关键指标:rows、type(ALL/index/range/ref/eq_ref/const)、key、Extra
- **优化器提示(Hint)**
  - 强制使用某索引:USE INDEX / FORCE INDEX
  - 强制 JOIN 顺序:STRAIGHT_JOIN
  - 用于优化器选错计划时的兜底
- **常见误判**
  - 数据倾斜(直方图未捕捉):优化器以为均匀分布选了错索引
  - 参数化查询的"参数嗅探"问题
  - 函数索引未识别
- **分布式优化器**
  - 额外考虑数据分片位置、网络代价
  - TiDB / CockroachDB / Spanner 都有分布式 CBO

## 和其他概念的关系

查询优化器决定 [[数据库索引]] 是否被使用,统计信息是其判断的依据。优化器与 [[MVCC]]、[[事务隔离级别]] 配合,生成符合一致性要求的计划。

[[慢查询优化]] 第一步几乎总是 EXPLAIN 看优化器选了什么计划、为什么。

[[关系型数据库]] 都有强大的优化器;[[NoSQL数据库]] 中 MongoDB 也有简化版优化器,Cassandra 因数据分片设计强制查询模式,几乎不需要优化器。

在 [[OLAP vs OLTP]] 数据仓库中,优化器更关注大表 JOIN、子查询展开、Star Schema 优化等。Spark SQL 的 Catalyst、Presto/Trino 的优化器都是分布式 CBO 的现代代表。
