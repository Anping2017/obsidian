# DDD领域驱动设计

## 定义

**领域驱动设计(Domain-Driven Design,DDD)** 是 Eric Evans 2003 年同名书提出的方法论:面对复杂业务系统,把对**领域(Domain)** 的深刻理解作为软件设计核心,通过持续与领域专家对话、用模型反映业务规则、按业务边界划分系统结构,而非按技术分层(Controller-Service-DAO)。

## 核心要点

- **战略层(Strategic Design)**
  - **通用语言(Ubiquitous Language)**:业务、产品、开发共用同一术语,贯穿代码、文档、对话。
  - **限界上下文(Bounded Context)**:同一术语在不同上下文可能含义不同——划清边界,各上下文内部模型自洽。
  - **上下文映射(Context Map)**:上下文之间的集成模式——共享内核、防腐层、客户-供应商、发布订阅等。
  - **核心域 / 支撑域 / 通用域**:精力分配——核心域必须 in-house 精雕细琢,支撑/通用可外包或买现成。
- **战术层(Tactical Design)**
  - **实体(Entity)**:有唯一标识、随时间状态变化的对象(用户、订单)。
  - **值对象(Value Object)**:无标识、不可变,以值相等(金额、地址、坐标)。
  - **聚合(Aggregate)**:一组紧密关联的对象,通过聚合根访问;事务一致性单位。
  - **领域服务(Domain Service)**:不属于任一实体的行为(转账涉及两账户)。
  - **领域事件(Domain Event)**:业务上有意义的发生(订单已创建);驱动 [[CQRS]]、[[事件溯源]]。
  - **仓储(Repository)**:聚合根的持久化抽象,屏蔽数据库细节。
  - **工厂(Factory)**:复杂聚合的构造逻辑封装。
- **架构整合**
  - **六边形架构(Ports & Adapters)** 与 **Clean Architecture** 是 DDD 友好的实现骨架。
  - **CQRS + Event Sourcing** 在写复杂、读简单的场景中常配合 DDD。
- **常见误区**
  - "贫血模型":只有 getter/setter,业务在 Service —— 退化为面向数据库编程。
  - 过度技术化:把 DDD 当架构八股文而非设计哲学。
  - 大而全:在简单 CRUD 应用强推 DDD 反而增加复杂度。

## 关系

- 与 [[BDD行为驱动开发]] 共享通用语言哲学——业务术语统一。
- 战术设计需要 [[面向对象编程]] 表达力,贫血模型是 DDD 反面。
- 与 [[微服务]] 强相关——限界上下文常成为服务拆分边界。
- [[CQRS]]、[[事件溯源]]、[[六边形架构]]、[[Clean Architecture]] 是 DDD 配套架构武器。
- [[设计模式]] 中工厂、仓储、策略等模式在 DDD 中频繁出现。
- 与 [[整洁代码]]、[[重构方法]] 互补——好设计 + 持续重构 = 可演化的领域模型。
