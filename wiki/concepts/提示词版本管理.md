# 提示词版本管理

## 定义

**提示词版本管理**(Prompt Version Management)是把 **prompt 视为可演进的代码资产**进行系统化管理的工程实践,涵盖**版本控制、变更审计、A/B 测试、灰度发布、效果监控、性能基准、回滚机制**等环节。它把 prompt 工程从"个人手工艺"提升为"团队工程化",是 LLM 应用进入生产环境必备的工程能力,也是 LLMOps(Large Language Model Operations)的核心组件之一。

## 核心要点

### 为何需要版本管理

- **prompt 直接影响产品行为**:微小改动可能改变用户体验
- **多人协作**:多个工程师 / 产品共同维护
- **多版本并存**:A/B 测试不同 prompt
- **追责与审计**:出现问题时可定位是哪次改动
- **回滚需求**:坏版本快速恢复
- **跨环境一致**:开发 / 测试 / 生产环境同步
- **跨模型迁移**:同 prompt 在不同模型表现不同

### 版本管理的核心要素

#### 1. Prompt 模板与变量分离

```yaml
# prompt.yaml
template_id: customer_summary_v2
version: 2.3.1
template: |
  你是 {role} 助手。
  请总结以下客户对话: {conversation}
  输出 {format} 格式。
variables:
  role: "客服质检"
  format: "JSON"
metadata:
  author: alice
  created: 2025-03-15
  tested_models: [gpt-4o, claude-3.5-sonnet]
  metrics:
    accuracy: 0.93
    avg_latency_ms: 1200
```

#### 2. 版本号语义

借鉴 SemVer:
- **主版本号(Major)**:破坏性变更,可能影响下游代码
- **次版本号(Minor)**:功能扩展,向后兼容
- **修订号(Patch)**:小修复

#### 3. 变更日志(Changelog)

每次提交记录:
- 改了什么(prompt diff)
- 为什么改(动机)
- 测试结果(对比指标)
- 风险评估
- 关联工单 / 反馈

#### 4. 关联测试集

每个 prompt 版本绑定:
- **回归测试集**:经典输入 + 期望输出
- **边界测试集**:破坏性输入
- **性能基准**:延迟、token、成本

### A/B 测试与灰度发布

#### A/B 测试设计

```python
def get_prompt(user_id):
    if hash(user_id) % 100 < 10:  # 10% 流量
        return prompts.v2_3_1
    else:
        return prompts.v2_2_5  # 旧版

# 跑一周后对比指标
# - 用户满意度评分
# - 任务完成率
# - 平均 token 消耗
# - 投诉率
```

#### 灰度发布(Canary Release)

新 prompt 逐步放量:
1. 1% 内部用户
2. 5% A 类用户
3. 25% 全用户
4. 100% 全量

每阶段监控指标,异常立即回滚。

### 效果监控

#### 在线指标

- **业务指标**:转化率、留存、NPS
- **质量指标**:人工评分、规则匹配率
- **效率指标**:平均 token、延迟、成本/请求
- **错误指标**:超时、解析失败、内容违规

#### 离线评估

- **黄金集**:固定测试集,每个版本回归
- **LLM-as-judge**:用更强模型评价输出
- **人工评估**:抽样人工打分
- **对抗测试**:专门构造的破坏性输入

### 回滚机制

- **触发条件**:核心指标下跌 > X%
- **回滚速度**:理想 < 5 分钟
- **数据保留**:回滚后保留新版本数据用于复盘
- **特征开关**:用 feature flag 控制 prompt 版本

### 主要工具与平台

| 工具 | 类型 | 特点 |
|---|---|---|
| **PromptLayer** | SaaS | 调用日志 + 版本管理 |
| **LangSmith(LangChain)** | SaaS | Trace + 评估 + 提示版本 |
| **Helicone** | 开源 + SaaS | 可观测性 + 缓存 |
| **Weights & Biases Prompts** | SaaS | 实验跟踪扩展 |
| **Humanloop** | SaaS | 协作式 prompt 工程 |
| **PromptHub** | 开源 | Git 风格 prompt 仓库 |
| **DSPy** | 框架 | 自动化优化 + 版本 |
| **Git + 自定义 CI** | DIY | 灵活但维护重 |

### 工程化实践

#### Prompt as Code

- prompt 文件存于代码仓库
- PR 流程审查 prompt 变更
- CI 跑 prompt 回归测试
- 与代码同步部署

#### Prompt 评审清单

代码评审之外,prompt 评审重点:
- [ ] 是否有明确的 system prompt?
- [ ] 是否有边界情况处理?
- [ ] 输出格式是否结构化?
- [ ] 是否考虑提示注入?
- [ ] 是否覆盖回归测试?
- [ ] 是否更新文档与 changelog?

#### Prompt 模板库

公司级共享:
- 通用任务模板(摘要、分类、提取)
- 行业模板(法律、医疗、金融)
- 角色模板(客服、销售、分析师)

### 与传统软件工程的差异

| 维度 | 传统代码 | Prompt |
|---|---|---|
| 决定性 | 强(同输入同输出) | 弱(温度 > 0 随机) |
| 测试 | 单元测试稳定 | 评估难,需 LLM-as-judge |
| 性能 | CPU/内存 | token + 延迟 |
| 调试 | 断点、日志 | 追溯链路 + 对比输出 |
| 重构 | 语义不变 | 语义可能变,需重测 |

### 主要挑战

- **prompt 与模型耦合**:换模型可能需要改 prompt
- **评估成本高**:LLM 评 LLM 也耗 token
- **评估不稳定**:同一答案不同时间评分可能不同
- **prompt 知识难复用**:每个领域 prompt 不同
- **与 RAG / Tools 协同**:prompt 不是孤立的

### 现代趋势

- **Prompt 编译器**:DSPy 把 prompt 编译为优化形式
- **Prompt 即合约**:类型系统 + 输出校验
- **Prompt 市场**:Hugging Face PromptHub 等共享平台
- **跨模型 prompt portability**:研究如何让 prompt 在多模型间兼容
- **Prompt 隐私**:某些 prompt 是商业机密

## 和其他概念的关系

提示词版本管理是 [[提示词工程]] 与 LLMOps 的桥梁。它与 [[元提示]] 中自动化 prompt 优化结合,使版本管理可半自动化。它支撑 [[少样本提示]]、[[思维链]]、[[ReAct提示]] 等具体技术在生产环境的稳定运行。它与 [[模型评估]] 紧密耦合,版本对比依赖评估能力。它涉及 [[提示注入]] 等安全议题——不当 prompt 改动可能引入风险。在 [[大语言模型应用栈]] 中,它是工程化层的关键组件。
