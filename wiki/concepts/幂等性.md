# 幂等性

## 定义

**幂等性(Idempotence)** 指对同一操作的多次执行,结果与执行一次完全相同。在分布式系统中,网络抖动、超时重试、消息重投是常态,接口若不幂等,重试会导致重复扣款、重复创建订单、重复发短信等灾难。**API 设计幂等是分布式系统的基本素养**。

## 核心要点

- **数学定义**
  - f(f(x)) = f(x)
  - 例:HTTP GET 自然幂等(读不影响状态);DELETE 幂等(删除一个 ID 多次结果相同);PUT 幂等(整体替换);POST 默认非幂等
- **HTTP 方法幂等性**

| 方法 | 幂等 | 安全(只读) |
|---|---|---|
| GET | 是 | 是 |
| HEAD | 是 | 是 |
| OPTIONS | 是 | 是 |
| PUT | 是 | 否 |
| DELETE | 是 | 否 |
| POST | 否 | 否 |
| PATCH | 否(可设计成是) | 否 |

- **典型非幂等场景**
  - **创建订单**:重复点击 / 网络重试导致两个订单
  - **支付扣款**:回调重试导致重复扣
  - **发短信 / 邮件**:用户收到多份
  - **MQ 消息消费**:消费者重启导致消息重投
- **幂等实现方法**
  - **唯一索引**
    - 业务级唯一键(订单号 / 流水号 / 业务 ID)建唯一约束
    - 重复 INSERT 报唯一冲突,业务捕获后返回已有结果
    - **优点**:强保证、简单
    - **缺点**:数据库压力大、错误处理需细致
  - **Token / 防重令牌**
    - 客户端先请求 token,提交时携带
    - 服务端校验 token 后立即作废
    - **场景**:Web 表单防重复提交
  - **状态机 + CAS**
    - 业务有状态(订单 INIT → PAID → CANCELED)
    - UPDATE ... WHERE status='INIT',只有第一次成功
    - **场景**:订单 / 支付状态推进
  - **分布式锁**
    - 见 [[分布式锁]],按业务 ID 加锁,串行处理
    - 简单粗暴,性能差
  - **数据库唯一日志表**
    - INSERT (request_id, status) 记录处理日志
    - 重复请求查表跳过
    - **场景**:消息消费幂等
  - **Redis SETNX**
    - request_id 作为 key,SET NX EX,先到先得
    - 性能好但 Redis 故障会破幂等
- **典型设计:支付幂等**
  - 客户端生成 client_id(UUID)
  - 调用 /pay {client_id, order_id, amount}
  - 服务端
    - 1. INSERT INTO pay_log(client_id) ON DUPLICATE → 重复请求直接返回已有结果
    - 2. 调三方支付
    - 3. 更新 pay_log 状态
  - 任何环节出错都可重试,client_id 是去重键
- **消息幂等(MQ 消费)**
  - **生产端**:发送时附带消息 ID(雪花 ID / UUID)
  - **消费端**:消费前检查"该消息 ID 是否处理过"(数据库 / Redis)
  - **At-least-once + 幂等 = Effectively-once**
  - Kafka / RocketMQ / RabbitMQ 都需要消费端幂等
- **HTTP 幂等键(Idempotency Key)**
  - Stripe / GitHub API 接受请求头 `Idempotency-Key: <uuid>`
  - 服务端 24 小时内对同 key 返回相同结果
  - 是行业标准做法
- **常见坑**
  - **只在数据库层做幂等,HTTP 层重试已造成日志重复**:需早期拦截
  - **幂等键不唯一**:用 user_id 而非 user_id + business_id,同用户多业务被误判
  - **幂等记录无过期**:存储无限增长
  - **超时回调状态不一致**:支付场景常见,需对账机制兜底

## 和其他概念的关系

幂等性是 [[分布式事务]] 中"重试 / 补偿"模式的基石。Saga / TCC 都假设各服务接口幂等,否则补偿无法安全执行。

[[消息队列]] 的"At-least-once"语义必须配合消费端幂等才能等价于"Exactly-once"。

[[熔断与降级]] 中重试机制依赖下游幂等,否则重试 = 重复执行。

[[RESTful API]] 设计原则要求 PUT/DELETE 幂等、POST 非幂等。设计 API 时声明幂等性是好习惯。

[[微服务]] 跨服务调用的可靠性几乎完全建立在幂等之上,是替代分布式事务的"穷人方案"且性价比最高。
