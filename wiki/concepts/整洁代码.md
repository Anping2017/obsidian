# 整洁代码

## 定义

**整洁代码(Clean Code)** 是 Robert C. Martin 2008 年同名书提出并系统化的代码写作哲学:代码读得多写得少,因此应优化"被理解的成本"而非"被写出的成本"。整洁代码不是少写代码,而是把意图表达到位,让下一个读者能在几秒理解此处在做什么、为什么。

## 核心要点

- **命名**
  - 用意图命名:`elapsedTimeInDays` 优于 `d`。
  - 避免误导:`accountList` 实际是 Map 就改名。
  - 同一概念一个词:不要既 fetch 又 retrieve 又 get 同义混用。
  - 类名用名词,方法名用动词。
- **函数**
  - **小**:理想 4-20 行,做一件事。
  - **单一抽象层级**:函数内不要混合不同抽象层级的语句。
  - **参数少**:0-3 个理想,避免 flag 参数,用对象封装。
  - **无副作用**:命名说做 X 就只做 X,不偷偷改全局状态。
- **注释**
  - 好代码不需要注释解释做什么——代码本身说清。
  - 注释解释"为什么"而非"做什么";警告、意图、引用法规适合写。
  - 注释会过期,优先重构而非加注释。
- **格式**
  - 文件按"报纸隐喻":重要在上、细节在下。
  - 概念上接近的代码物理上靠近。
- **错误处理**
  - 抛异常优于返回错误码。
  - 不要用异常做控制流。
  - 不返回 null,不接受 null —— 用 Optional/null object。
- **DRY 与 KISS**
  - **DRY**:Don't Repeat Yourself;但不要为消除"看似"重复创造错误抽象。
  - **KISS**:Keep It Simple, Stupid;过度设计是另一种债。
- **童子军军规**:每次提交后代码比之前更整洁——持续小改胜过偶尔大重构。

## 关系

- 与 [[设计原则SOLID]]、[[设计模式]] 在不同抽象层共同改善代码质量。
- [[TDD测试驱动开发]] 是整洁代码的最佳实践——测试先行强迫小函数与依赖注入。
- [[重构方法]] 是把不洁代码改为整洁的具体技术。
- 在 [[代码评审]] 中,整洁代码的多数规则是评审清单。
- 与 [[Clean Architecture]]、[[六边形架构]] 是同思想在不同尺度的体现。
- 与 [[技术债管理]] 相反相成——整洁代码是降债工具,债越少越易整洁。
