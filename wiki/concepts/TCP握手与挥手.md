# TCP 握手与挥手

## 定义

**TCP(Transmission Control Protocol)** 是面向连接的、可靠的、基于字节流的传输层协议。它通过**三次握手(Three-Way Handshake)** 建立连接、**四次挥手(Four-Way Handshake)** 关闭连接,通过序列号(Sequence Number)、确认号(ACK)、滑动窗口、超时重传等机制在不可靠的 IP 网络上实现可靠传输。是 [[HTTP协议]]、SSH、数据库、邮件等几乎所有可靠通信的底层。

## 核心要点

- **TCP 报文段关键字段**
  - **Source Port / Dest Port**:端口
  - **Sequence Number**:本段第一个字节的序号
  - **Acknowledgement Number**:期望收到的下一字节序号
  - **Flags**:SYN(同步) / ACK(确认) / FIN(结束) / RST(重置) / PSH / URG
  - **Window**:接收窗口,流控用
  - **Checksum**:校验和
- **三次握手(建立连接)**
  - **目的**:双方确认能收能发,协商初始序列号(ISN)
  - **流程**
    - 1. 客户端 → 服务端:**SYN**, seq=x(第一次)
    - 2. 服务端 → 客户端:**SYN+ACK**, seq=y, ack=x+1(第二次)
    - 3. 客户端 → 服务端:**ACK**, seq=x+1, ack=y+1(第三次)
  - **为什么三次而非两次**
    - 两次握手:服务端不知道客户端是否还在;客户端的旧 SYN 包延迟到达会让服务端误开连接
    - 三次:双方都确认对方的发送和接收能力
- **四次挥手(关闭连接)**
  - **目的**:双方各自关闭自己方向的发送(全双工独立关闭)
  - **流程**
    - 1. 客户端 → 服务端:**FIN**, seq=u(我没数据要发了)
    - 2. 服务端 → 客户端:**ACK**, ack=u+1(收到,但我可能还有数据要发)
    - 3. 服务端 → 客户端:**FIN**, seq=v(我也发完了)
    - 4. 客户端 → 服务端:**ACK**, ack=v+1(收到,关闭)
  - **为什么四次而非三次**
    - 服务端收到 FIN 后,不能立即回 FIN,因为可能还有数据要传
    - 第二次和第三次拆开,等服务端处理完
- **TIME_WAIT 状态**
  - 主动关闭方在最后一个 ACK 后进入 TIME_WAIT,等 2MSL(Maximum Segment Lifetime,通常 60s)再 CLOSED
  - **目的**
    - 1. 确保最后 ACK 到达对方;若对方未收到会重发 FIN,本端能再回 ACK
    - 2. 让网络中残留的本连接的延迟报文消亡,不影响下一连接
  - **副作用**:大量 TIME_WAIT 占用端口与资源,服务端高并发场景常见问题
  - **缓解**:tcp_tw_reuse(重用)、SO_REUSEPORT、长连接复用
- **可靠性机制**
  - **序列号 + ACK**:发送方知道哪段被确认
  - **超时重传(RTO)**:未及时 ACK 的段重发
  - **滑动窗口**:不必等每段 ACK 才发下一段,提升吞吐
  - **快速重传**:收到 3 个重复 ACK 立即重传,而非等超时
- **流量控制 vs 拥塞控制**
  - **流量控制(Flow Control)**:接收方告诉发送方自己缓冲区还能收多少(receiver window)
  - **拥塞控制(Congestion Control)**:发送方根据网络丢包动态调速
    - **慢启动(Slow Start)**:cwnd 指数增长
    - **拥塞避免**:线性增长
    - **快重传 / 快恢复**:丢包时不至于重新慢启动
    - **算法**:Reno / Cubic(Linux 默认)/ BBR(Google,基于带宽时延)
- **常见问题**
  - **半连接攻击(SYN Flood)**:攻击者发大量 SYN 不回 ACK,耗尽服务端连接表;防御:SYN Cookie
  - **粘包/拆包**:TCP 是字节流不分包,应用层需自定义边界(长度前缀 / 分隔符)
  - **Nagle 算法 vs delayed ACK**:小包合并 vs 延迟确认,组合可能导致延迟,实时场景需关闭(TCP_NODELAY)
- **TCP vs UDP**

| 特性 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠 | 不可靠 |
| 顺序 | 有序 | 无序 |
| 速度 | 慢 | 快 |
| 头部 | 20 字节 | 8 字节 |
| 用途 | HTTP/SSH/DB | DNS/视频/游戏 |

- **TCP 在新协议中的演进**
  - **HTTP/3 + QUIC**:基于 UDP 重新实现可靠传输,减少握手延迟
  - **TFO(TCP Fast Open)**:握手时携带数据,减少 1RTT
  - **MPTCP**:多路径 TCP,Wi-Fi+蜂窝同时传

## 和其他概念的关系

TCP 是 [[HTTP协议]] 的底层运输,几乎所有 [[关系型数据库]]、[[消息队列]]、RPC 调用都基于 TCP。

TCP 与 TLS 配合提供安全可靠通信,见 [[TLS]]。

在 [[微服务]] 中,服务间长连接(HTTP/2、gRPC)避免反复握手开销;[[负载均衡]] 的 L4 模式直接转发 TCP 流量,无需解析应用层。

性能调优(TIME_WAIT、Backlog、Keepalive)是 [[慢查询优化]] 之外服务端运维的另一日常。

QUIC / HTTP3 用 UDP 模拟 TCP 是为了规避 TCP 的队头阻塞与 1-3 RTT 握手代价。
