# 多版本并发控制 MVCC

## 定义

多版本并发控制(Multi-Version Concurrency Control, MVCC)是一种**数据库并发控制技术**,通过**为每行保留多个历史版本**,使**读操作和写操作可以并发执行而互不阻塞**:

- 读取任意时刻看到的是某个时间点的「快照」
- 写入产生新版本,不覆盖旧版本
- 旧版本在没有事务可见时由后台 GC(Vacuum/Purge)回收

(本文与 [[MVCC]] 同一概念)

## 核心要点

### 解决了什么问题

传统**两阶段锁(2PL)** 用读写锁实现隔离,代价是:

- 长事务持有锁,阻塞其他事务
- 读操作互相不阻塞,但读写互斥
- 死锁难以避免

MVCC 通过空间换并发,把读写矛盾大幅缓和。

### 工作原理(简化)

每行加两个隐式列:

- `xmin`:创建该版本的事务 ID
- `xmax`:删除/失效该版本的事务 ID(若存在)

事务读取时:

- 拿到自己的事务 ID 与活跃事务列表
- 只能看到 `xmin ≤ 自己 且 xmax > 自己 或为空` 的版本
- 实现快照隔离

### 主流实现差异

| 数据库 | 实现 |
|---|---|
| PostgreSQL | 行多版本直接存 heap 文件,VACUUM 后台清理 |
| MySQL InnoDB | 旧版本存 undo log,可用于回滚和读快照 |
| Oracle | 类似 InnoDB,undo 段 + 回滚段 |
| SQL Server | 可选启用 RCSI(Read Committed Snapshot Isolation) |

### 隔离级别中的角色

MVCC 通常实现**快照隔离(Snapshot Isolation)** 或更严格的**可串行化快照隔离(SSI)**,大致对应 SQL 标准的 REPEATABLE READ 或 SERIALIZABLE:

- 不会出现脏读、不可重复读
- 但快照隔离仍可能有「写偏斜」(Write Skew),需 SSI 或 SELECT FOR UPDATE 防范

### 代价

- **存储膨胀**:旧版本占空间,长事务延缓 GC 加剧问题
- **GC 压力**:VACUUM/PURGE 是 PG/MySQL 性能调优的常见话题
- **索引膨胀**:旧版本对应的索引项也需清理
- **长事务伤害**:可能导致表膨胀、统计信息失真、查询计划退化

## 和其他概念的关系

MVCC 是 [[数据库]] 实现 [[ACID]] 中 Isolation 的两条主线之一(另一条是 [[数据库锁机制]]),与 2PL 互补。

[[OLAP与OLTP]] 中,OLTP 系统强烈依赖 MVCC 让长查询不阻塞业务事务;OLAP 系统多用列存与分析快照,MVCC 不那么关键。

[[分布式事务]] 在 MVCC 基础上扩展为 MVCC + 共识(如 TiDB 的 Percolator-like 模型);[[Spanner]] 用 TrueTime API 保证全局快照。

理解 MVCC 是理解 PostgreSQL 与 MySQL 性能调优的关键——许多看似奇怪的现象(如 VACUUM 卡死、表空间不释放、长查询导致写入慢)都源自 MVCC 内部机制。
