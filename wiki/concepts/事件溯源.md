# 事件溯源

## 定义

**事件溯源(Event Sourcing)** 是把领域对象的所有状态变更建模为**不可变事件序列**并持久化的模式。当前状态不再单独存储,而是通过从初始状态重放事件流得出。它把"现在是什么"换成"发生过什么",带来天然的审计轨迹与时间旅行能力。

## 核心要点

- **核心结构**
  - **Event Store**:append-only 事件日志,按聚合 ID 分片;EventStoreDB、Kafka、PostgreSQL 都可承担。
  - **聚合(Aggregate)**:在内存里通过 `apply(event)` 重建状态;接到命令时校验不变量、产出新事件。
  - **快照(Snapshot)**:定期把聚合状态写入,加速重建,避免每次重放百万事件。
  - **投影(Projection)**:订阅事件流构造读模型,服务查询。
- **优势**
  - **完整审计**:每次变更都有"是谁、何时、为何"的事件记录;合规友好。
  - **时间旅行**:重放到历史任一时点,调试与回归分析方便。
  - **业务洞察**:事件流是数据科学一手原料,无需额外埋点。
  - **CQRS 自然集成**:写到 Event Store、读从投影,扩展性好。
  - **消息驱动集成**:事件可发布给其他上下文(微服务)消费。
- **代价与挑战**
  - **事件版本演进**:业务变化导致事件结构改变——需要版本字段、上转换器(Upcaster)。
  - **重构难度**:历史事件不可改,新模型必须能解释旧事件。
  - **查询难**:查询当前状态需投影,复杂度上升。
  - **最终一致性**:投影滞后于事件,UX 设计需配合。
  - **GDPR / 删除权**:不可变设计与"被遗忘权"冲突,需 crypto-shredding 等方案。
- **典型场景**:金融交易、订单/库存、合规系统、物联网状态机、协作编辑(如 Git/Operational Transformation)。

## 关系

- 与 [[CQRS]] 是经典搭档,但 ES 不必然 CQRS、CQRS 也不必然 ES。
- 与 [[DDD领域驱动设计]] 战术上深度契合——领域事件是聚合行为的自然产物。
- 依赖 [[消息队列]]/事件流(Kafka)做跨服务传播。
- 与 [[ACID事务]] 取舍——单聚合内强一致,跨聚合采用 Saga / 补偿事件。
- 与 [[Git版本控制]] 哲学相通——都是"内容寻址 + 不可变追加"。
