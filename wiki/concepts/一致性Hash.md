# 一致性 Hash Consistent Hashing

## 定义

**一致性哈希(Consistent Hashing)**是 1997 年 David Karger 等在 MIT 提出的分布式哈希算法,目标是解决**节点增减导致大规模重映射**的问题。

普通哈希分片(`node = hash(key) % N`)在节点数 N 变化时,几乎所有键的归属都会变,触发海量数据迁移。
一致性哈希把**节点和键都映射到一个环(0 到 2³² 或 2⁶⁴)**,键归属于沿环顺时针遇到的第一个节点。节点增减只影响相邻段,迁移量从 O(M) 降到 O(M/N),M 是键总数,N 是节点总数。

## 核心要点

### 工作机制

1. 把每个节点的 ID(IP+端口)用哈希函数映射到环上一个点
2. 把每个键也哈希到环上一个点
3. 键归属于沿环顺时针遇到的第一个节点
4. 增加节点 X:它接管前驱节点到自己之间这段的键
5. 删除节点 Y:其原管区交给后继节点

### 为何"一致":数学性质

- **平衡性**(Balance):键大致均匀分布到节点
- **单调性**(Monotonicity):新增节点不会让"已有正确分配的键"被打乱(只迁部分到新节点)
- **分散性**(Spread):同一键不同时被多个节点同时认为"我的"
- **负载性**(Load):每节点不会接到压倒性份额

### 数据倾斜与虚拟节点(Virtual Node)

仅几个节点时哈希环上分布不均,某些节点会承担过多负载。
**解决**:每个物理节点放置多个虚拟节点(如 100-500 个),环上点更密集,负载更均衡。
Redis Cluster、Memcached 客户端、Cassandra 都用虚拟节点。

### 经典应用

1. **分布式[[缓存]]**:Memcached、Redis 客户端分片(Twemproxy、ShardedJedis)
2. **DynamoDB**(Amazon):核心论文 Dynamo 用一致性哈希做数据分区
3. **Cassandra**:节点环 + token 范围,即一致性哈希
4. **Apache Kafka**:Producer 默认按 key hash 选 partition;不过 Kafka 不是一致性哈希(分区数固定)
5. **CDN 路由**:把用户 IP 一致性哈希到边缘节点
6. **[[负载均衡]]**:Nginx 的 `hash $remote_addr consistent;`,故障切换迁移最小
7. **分布式存储**:Ceph 的 CRUSH 算法是一致性哈希的高级演化

### 与普通哈希分片对比

假设 100 万 key 分布在 10 个节点,新增 1 节点:
- 普通 `hash % N`:从 N=10 变 N=11,**~91% 的 key 重映射**
- 一致性哈希:新节点接管原 10 个节点中的 1 个的部分键,**~9% 重映射**

### 局限

- 实现比 `hash % N` 复杂
- 极端坏哈希仍可能倾斜(虚拟节点缓解)
- 节点性能不均时单虚拟节点数应加权配置

### Jump Consistent Hash(2014, Google)

Lamping & Veach 提出的更精巧算法:无需保存环结构,O(log N) 时间内确定 key 归属节点,自然均衡。但**不支持任意节点删除**(只能从尾部减),适合**只增不减或固定节点 ID 顺序**的系统。

### Maglev Hash(Google 论文)

Google 负载均衡器用的查表算法,O(1) 查询,扩展时迁移量约 1/N。在 Envoy、Kubernetes 中应用。

## 和其他概念的关系

一致性哈希与[[Hash表]]同源,在分布式语境下推广。它和[[负载均衡]]、[[缓存]]系统、[[NoSQL数据库]]密切相关 —— 几乎所有"按 key 分片"的分布式存储都用它或其变体。

[[微服务]]在 API Gateway 实现"会话粘性(Sticky Session)"时常用一致性哈希:同一用户的请求路由到同一后端实例,有利于缓存和有状态处理。

CDN 节点选择、[[消息队列]]按 key 路由到 partition、分布式锁的 key 分片都依赖类似思路。理解一致性哈希是理解大规模分布式系统数据布局的钥匙。
