# 六边形架构

## 定义

**六边形架构(Hexagonal Architecture)** 又称 **端口与适配器(Ports and Adapters)**,由 Alistair Cockburn 2005 年提出。核心想法:把业务领域逻辑放在中央六边形,外部世界(UI、数据库、消息队列、第三方 API)通过**端口(Port,接口)**与**适配器(Adapter,实现)** 接入。领域不依赖任何外部技术,可被独立测试和演化。

## 核心要点

- **端口分类**
  - **驱动端口(Driving / Inbound)**:外部主动调用领域(HTTP API、CLI、定时任务)。
  - **被驱动端口(Driven / Outbound)**:领域调用外部资源(仓储、邮件、消息发送)。
- **依赖方向**:外部依赖内部,内部用接口表达需求,外部提供实现 —— [[依赖倒置]] 在架构层面落地。
- **典型分层**
  - **Domain**:实体、值对象、领域服务,纯业务逻辑。
  - **Application**:用例(Use Case)/服务,编排领域对象、定义端口。
  - **Adapters**:HTTP Controller、数据库 Repository 实现、消息消费者、SMTP 发送器。
- **优势**
  - **可测试性**:用 in-memory 适配器替代真实数据库即可单元测试领域。
  - **可替换性**:从 PostgreSQL 切到 DynamoDB 只换适配器,核心不动。
  - **多入口支持**:同一用例可被 REST、GraphQL、CLI、消息队列触发。
  - **业务先行**:架构提醒"先写领域,基础设施其次"。
- **与 Onion / Clean Architecture 关系**
  - 三者本质等价——同心圆 + 依赖方向向内。
  - Clean Architecture(Bob Martin)进一步细分为 Entity / Use Case / Interface Adapter / Frameworks 四圈。
- **常见反模式**
  - 端口接口被实现细节污染(返回 ORM 实体、抛 SQLException)。
  - 用例层成为"事务脚本",领域贫血。
  - 把所有数据库表都包成仓储——仓储应面向聚合而非表。

## 关系

- 是 [[DDD领域驱动设计]] 推荐的代码结构骨架。
- [[Clean Architecture]] 是六边形架构的 Bob Martin 版本扩展。
- 与 [[CQRS]]、[[事件溯源]] 兼容——Command/Query 端口、事件投影适配器。
- 与 [[微服务]] 互补——服务内部用六边形,服务间用消息/REST。
- 落地需要良好的 [[设计模式]](策略、适配器、工厂)与 [[设计原则SOLID]]。
