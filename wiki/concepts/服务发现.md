# 服务发现

## 定义

**服务发现(Service Discovery)** 是分布式系统中让服务消费者动态找到服务提供者位置(IP+端口)的机制。在 [[微服务]] 与容器化架构下,实例频繁启停、扩缩容、故障转移,硬编码 IP 无法运转,服务发现成为基础组件。

## 核心要点

- **核心问题**
  - 服务实例的 IP / 端口随调度变化(K8s 自动调度、自动扩缩容)
  - 消费者要在不重启情况下找到当前可用的实例列表
  - 需要健康检查剔除挂掉的实例
- **两种模式**
  - **客户端发现(Client-Side Discovery)**
    - 消费者直接查询注册中心,获取实例列表后自己负载均衡
    - 优势:少一跳、灵活
    - 劣势:每语言要 SDK
    - 例:Eureka + Ribbon、Nacos SDK、gRPC + xDS
  - **服务端发现(Server-Side Discovery)**
    - 消费者发请求给 LB / API Gateway,由其查注册中心后转发
    - 优势:多语言友好、SDK 简单
    - 劣势:多一跳、LB 成瓶颈
    - 例:K8s Service + kube-proxy、AWS ALB + Target Group
- **注册中心实现**
  - **Eureka(Netflix)**
    - AP 优先,自我保护机制(网络问题不剔除实例)
    - Spring Cloud 早期标配,2.0 已闭源
  - **Consul(HashiCorp)**
    - CP 优先,基于 [[Raft共识算法]]
    - DNS + HTTP API,跨数据中心
    - 内置 KV、健康检查
  - **etcd**
    - 基于 Raft 的 KV 存储,K8s 元数据存储
    - 服务发现是 KV 用法之一
  - **ZooKeeper**
    - Zab 协议(类 Paxos),CP
    - Dubbo / Kafka 旧版本依赖
  - **Nacos(阿里)**
    - 既支持 AP(类 Eureka)也支持 CP(类 ZK),配置 + 注册一体
- **K8s 内置服务发现**
  - **Service**:Pod 集合的虚拟 IP + DNS
  - **kube-proxy**:在每节点上实现 Service 的 iptables/IPVS 转发
  - **CoreDNS**:Pod 内部域名解析
  - 应用直接用 service-name 访问,K8s 解析为 Cluster IP
  - 见 [[Kubernetes]]
- **健康检查**
  - **被动**:实例定时心跳(heartbeat),失联即剔除
  - **主动**:注册中心 / LB 探活(HTTP/TCP/gRPC 探针)
  - **K8s**:liveness / readiness / startup probe 三类
- **服务注册流程**
  - 1. 服务启动 → 把 (服务名, IP, 端口, 元数据) 注册到中心
  - 2. 持续心跳保活
  - 3. 优雅下线:先发"下线"再退出,避免请求路由到已死实例
- **CAP 取舍**
  - **AP 注册中心(Eureka/Nacos AP 模式)**:网络分区时仍可注册查询,可能读到过期数据
  - **CP 注册中心(Consul/etcd/ZK)**:网络分区时少数派不可用,但保证一致
  - 见 [[CAP定理]]
- **服务网格中的服务发现**
  - [[服务网格]] sidecar 拦截所有出向流量,自动从控制面拉取服务列表
  - Envoy + xDS 协议(EDS 是 Endpoint Discovery Service)
  - 应用代码完全无感
- **DNS 服务发现**
  - 简单场景用 DNS 多 A 记录或 SRV 记录
  - 优点:语言无关,客户端只需 DNS 解析
  - 缺点:DNS 缓存导致变更延迟,无健康检查
- **典型反模式**
  - 配置文件硬编码 IP:扩缩容必须重启
  - 长 DNS 缓存:实例变化无法快速感知
  - 不优雅下线:请求飞奔到已死实例

## 和其他概念的关系

服务发现是 [[微服务]] 架构的基础设施,与 [[负载均衡]]、[[API网关]] 紧密协作:LB / 网关从注册中心拉取实例列表,然后做流量分发。

[[CAP定理]] 决定注册中心选型:Consul/ZK/etcd 是 CP,Eureka/Nacos AP 模式是 AP。底层实现依赖 [[Raft共识算法]] 或 [[Paxos]]。

[[服务网格]] 把服务发现下沉到 sidecar,应用代码彻底解耦。

[[Kubernetes]] 把服务发现内置为 Service + DNS,简化常见场景,大型企业可叠加 Istio 等服务网格做精细控制。

[[配置中心]](Apollo、Nacos)与服务发现常在同一注册中心实现,共用一致性后端。
