# 依赖注入与控制反转

## 定义

**控制反转(Inversion of Control,IoC)** 是一种设计原则——**把对象创建、依赖装配的控制权从调用代码转交给框架/容器**。它的另一面是"反转":传统代码"我创建依赖、我用",IoC 是"框架给我依赖、我用"。

**依赖注入(Dependency Injection,DI)** 是 IoC 最常见的实现方式:**对象通过构造函数、属性或方法接收依赖,而不是自己 new**。

二者紧密相关但不等价:DI 是 IoC 的一种(还有服务定位器、模板方法、事件等其他 IoC 模式)。Martin Fowler 在 2004 年《Inversion of Control Containers and the Dependency Injection pattern》区分了二者。

## 没有 DI 的代码

```python
class OrderService:
    def __init__(self):
        self.db = MySQLDatabase("localhost", 3306)  # 硬依赖
        self.payment = StripePayment(api_key="...")  # 硬依赖
        self.email = SMTPEmailSender("smtp.gmail.com")  # 硬依赖

    def place_order(self, order):
        self.db.save(order)
        self.payment.charge(order.amount)
        self.email.send(order.user.email, "order confirmed")
```

**问题**

1. **难测试**:测试 OrderService 必须连真 MySQL、真 Stripe、真 SMTP
2. **难替换**:换 MongoDB 要改 OrderService 代码
3. **紧耦合**:OrderService 知道太多 MySQLDatabase 细节
4. **配置散乱**:连接串、密钥到处都有

## 用 DI 重构

```python
class OrderService:
    def __init__(self, db: Database, payment: PaymentGateway, email: EmailSender):
        self.db = db
        self.payment = payment
        self.email = email

    def place_order(self, order):
        self.db.save(order)
        self.payment.charge(order.amount)
        self.email.send(order.user.email, "order confirmed")

# 装配(Composition Root)
db = MySQLDatabase(...)
payment = StripePayment(...)
email = SMTPEmailSender(...)
service = OrderService(db, payment, email)
```

**好处**

1. **可测试**:test 时传 mock 依赖
2. **可替换**:换实现不改 OrderService
3. **解耦**:OrderService 只依赖接口
4. **配置集中**:只在一个地方装配

## DI 的三种风格

**1. 构造函数注入(推荐)**

```java
public class OrderService {
    private final Database db;
    private final PaymentGateway payment;

    public OrderService(Database db, PaymentGateway payment) {
        this.db = db;
        this.payment = payment;
    }
}
```

**优点**:
- 不可变(final)
- 依赖明确(看构造器即知)
- 编译期保证(必填)

**2. Setter / 属性注入**

```java
public class OrderService {
    @Autowired
    private Database db;
    @Autowired
    private PaymentGateway payment;
}
```

**缺点**:
- 可变(可被改)
- 依赖隐藏
- 创建后未必完全初始化

**3. 接口注入(罕见)**

依赖通过 implements 注入接口实现。理论存在,实践少。

**主流共识:构造函数注入优先**(Spring、Angular 都默认推荐)。

## IoC 容器

容器自动管理对象的创建、装配、生命周期:

**Spring(Java)**

```java
@Service
public class OrderService {
    private final Database db;

    public OrderService(Database db) {
        this.db = db;
    }
}

@Component
public class MySQLDatabase implements Database { ... }
```

Spring 启动时:
1. 扫描 @Component / @Service 注解
2. 注册 Bean 到容器
3. 解析依赖图
4. 按顺序创建并注入

**典型注解**

- @Component / @Service / @Repository / @Controller:声明 Bean
- @Autowired:注入依赖
- @Qualifier:选具体实现
- @Configuration / @Bean:Java 配置

## 主流 DI 框架

**Java/Kotlin**

- **Spring**:全栈最大,[[Spring Boot]] 内核
- **Guice**(Google):轻量
- **Dagger**(Android):编译期 DI,无反射

**Python**

- **dependency-injector**:显式声明
- **FastAPI Depends**:基于函数参数
- **Inject**:简单

**C#**

- **Microsoft.Extensions.DependencyInjection**:.NET Core 内置
- **Autofac**、**Ninject**:第三方

**TypeScript / JavaScript**

- **NestJS** 内置
- **InversifyJS**:类似 Spring
- **TSyringe**

**Swift**

- **Swinject**

**Rust**

- 较少专属框架(类型系统不如 Java 灵活)
- 手动构造或 Builder 模式

## NestJS 示例(TypeScript)

```typescript
@Injectable()
export class OrderService {
  constructor(
    @Inject('Database') private db: Database,
    private payment: PaymentService,
  ) {}

  async placeOrder(order: Order) {
    await this.db.save(order)
    await this.payment.charge(order.amount)
  }
}

@Module({
  providers: [
    OrderService,
    { provide: 'Database', useClass: MySQLDatabase },
    PaymentService,
  ],
})
export class OrderModule {}
```

NestJS 借鉴 Angular,模块化 + 依赖注入,Node 生态最像 Spring。

## SOLID 中的 D:依赖倒置

依赖倒置原则(Dependency Inversion Principle):
- 高层模块不应依赖低层模块,二者都应依赖抽象
- 抽象不应依赖具体,具体应依赖抽象

DI 是依赖倒置的工具——通过注入接口而非具体类,自动实现倒置。这是 [[设计原则SOLID]] 的"D"。

## 测试中的价值

**没有 DI**

```python
def test_order_service():
    # 必须连真 MySQL、真 Stripe
    service = OrderService()
    service.place_order(order)
    # 副作用:真扣款!真发邮件!
```

**有 DI**

```python
def test_order_service():
    mock_db = Mock()
    mock_payment = Mock()
    mock_email = Mock()
    service = OrderService(mock_db, mock_payment, mock_email)
    service.place_order(order)
    mock_payment.charge.assert_called_once_with(100)
```

测试快、隔离、可重复。这是 DI 在 [[TDD测试驱动开发]] 中的关键。

## AOP(面向切面)与 DI

DI 框架常带 AOP 能力——围绕方法调用切入横切关注点(日志、事务、缓存):

```java
@Service
@Transactional
public class OrderService {
    @Cacheable("orders")
    public Order get(Long id) { ... }
}
```

@Transactional 让 Spring 在方法前后自动开始/提交事务。这是 [[设计模式]] 中代理模式的工业化。

## 容器 vs 服务定位器

**服务定位器(Service Locator)**

```java
public class OrderService {
    public void placeOrder(Order o) {
        Database db = ServiceLocator.get(Database.class);  // 主动取
        db.save(o);
    }
}
```

**问题**

- 依赖不明显(看代码看不出依赖)
- 测试时需要 mock ServiceLocator
- 与 IoC 哲学相反(还是"我控制")

DI 优于服务定位器,Mark Seemann《Dependency Injection in .NET》详细论证。

## 反模式

**1. Field 注入用太多**

```java
@Autowired
private Database db;
```

构造器更好,显式 + 不可变。

**2. 容器变成上帝对象**

不加节制把所有类放到容器,失去模块边界。

**3. 循环依赖**

A 注 B,B 注 A。Spring 部分支持(Setter)但是设计气味,应重构。

**4. 滥用 @Autowired**

什么都标 @Autowired,接口隔离原则被破坏。

**5. 服务定位器伪装**

```java
applicationContext.getBean(Database.class)  // 实质上是定位器
```

这是退化,应避免。

## 局限

- **学习成本**:新人不懂"魔法"
- **运行时开销**:反射、代理(Spring 启动慢部分原因)
- **调试链长**:堆栈深
- **过度抽象**:每个类一个接口,接口爆炸
- **静态分析弱**:依赖在运行时装配,IDE 跳转有时不准

## 现代趋势

- **编译期 DI**:Dagger、Hilt(Android)、Macro(Rust)避免反射
- **函数式 DI**:Haskell / 函数式语言用 Reader Monad / 显式参数
- **轻量替代**:Go / Rust 偏向手动构造,反对"魔法容器"
- **轻量的 React/Vue**:无 DI,组件直接 import 工具函数

不是所有语言都需要重 DI 容器,Go / Rust 用"显式构造 + 接口"也工作得很好。

## 和其他概念的关系

DI 是 [[设计原则SOLID]] 中依赖倒置原则的工业化,与 [[设计模式]] 中工厂、抽象工厂、策略模式深度相关。它是 [[Spring Boot]]、Angular、[[NestJS]] 等现代框架的灵魂。

DI 让 [[TDD测试驱动开发]] 成为可能——可测性是好设计的副产物。它与 AOP 配合实现"横切关注点"(日志、事务、安全)的优雅切入,是 [[微服务]] 时代代码组织的核心方法论。

它体现的"配置与代码分离"哲学与 [[CI_CD流水线]] 中的 Infrastructure as Code、Docker 中环境变量配置等思想一脉相承——把"是什么"与"怎么用"解耦。
