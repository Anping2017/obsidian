# 分布式追踪 Distributed Tracing

## 定义

**分布式追踪(Distributed Tracing)** 是一种可观测性技术:在一个请求穿越多个服务、消息队列、数据库的过程中,通过传递唯一 **Trace ID** 和分段 **Span**,把整个调用链记录为可视化的时间线。

它由 Google 2010 年的论文《Dapper: a Large-Scale Distributed Systems Tracing Infrastructure》系统化,后衍生出 Zipkin(Twitter)、Jaeger(Uber)、SkyWalking(华为)等开源实现,2019 年起 OpenTelemetry 成为统一标准。

分布式追踪是 [[可观测性三支柱]] 之一,与日志、指标互补——它回答"**这个请求慢在哪一步**"。

## 核心概念

**Trace**

一个用户请求的完整端到端旅程。从用户点击 → 网关 → 服务 A → 服务 B → 数据库 → 缓存 → 响应返回,整体一个 Trace。

**Span**

Trace 中的一段操作。每个 Span 包含:
- span_id(唯一)
- trace_id(归属)
- parent_span_id(父 Span)
- 操作名(operation name)
- 起止时间
- Tags(键值对元数据)
- Logs(事件)
- Status(成功 / 失败 / 错误)

**Context Propagation**

跨服务传递 Trace ID + Span ID 的机制:
- HTTP Header(traceparent、b3-traceid 等)
- gRPC metadata
- Kafka 消息 Header
- 数据库连接(部分支持)

## OpenTelemetry(OTel)

**统一标准的尝试**

OpenTelemetry 是 OpenTracing(2016)+ OpenCensus(2017,Google)合并的产物,2019 年成为 CNCF 项目。它提供:
- 跨语言 SDK(Java、Go、Python、Node、.NET、Rust 等)
- 统一数据模型(Trace、Metrics、Logs)
- 自动 instrumentation(框架自动埋点)
- OTel Collector(中转、采样、批处理)
- 后端无关(可发往 Jaeger、Zipkin、Datadog、Honeycomb 等)

**埋点示例(Python)**

```python
from opentelemetry import trace
tracer = trace.get_tracer("my.service")

with tracer.start_as_current_span("process_order") as span:
    span.set_attribute("order.id", order_id)
    span.set_attribute("user.id", user_id)
    process(order)
    span.set_status(Status(StatusCode.OK))
```

自动 instrumentation 进一步:加 SDK + opentelemetry-instrumentation-flask,Flask 路由自动有 Span,无需改代码。

## Jaeger 与 Zipkin

**Jaeger(2015,Uber)**

- 开源,CNCF 毕业项目
- Go 写,性能好
- 存储后端:Cassandra / Elasticsearch / Memory
- UI:Trace 时间线、依赖图、对比 Trace
- 与 OTel 完全兼容(2023 后 Jaeger v2 全面 OTel 化)

**Zipkin(2012,Twitter)**

- 老牌,Java 写
- 存储:MySQL / Cassandra / ES
- UI 较简陋
- 仍有大量用户但发展放缓

二者协议(Zipkin v1/v2、Jaeger Thrift)被 OTel 统一,后端选择更多看运维偏好。

## 商业可观测平台

| 平台 | 特点 |
|---|---|
| Datadog APM | 全栈,贵,DX 优 |
| New Relic | 老牌 APM |
| Honeycomb | 高基数查询强,工程文化 |
| Lightstep(ServiceNow) | 因果追踪、SLO |
| Splunk Observability | 企业 |
| Dynatrace | AI 自动诊断 |
| Tempo(Grafana Labs) | 开源,与 [[Grafana]] 整合 |

商业平台优势:不用自己运维存储,SLO 计算、异常检测、AI 分析等高级功能。劣势:贵,数据出域风险。

## 工程价值

**1. 慢请求定位**

P99 5 秒的接口,Trace 图一看:数据库慢查 4 秒。无需多服务跨系统翻日志。

**2. 跨服务故障传播**

服务 A 报错的真正原因可能在服务 D。Trace 直接展示完整路径,定位"病根"。

**3. 性能优化**

发现:N+1 查询、串行 API 可并行、不必要外部调用。

**4. 服务依赖可视化**

Trace 数据聚合成 Service Map,自动画出当前架构。

**5. SLO / SLI 度量**

按操作名聚合 Span 延迟分位数,作为 SLO 指标源。

## 采样策略

100% 采样不现实(成本爆炸),常用策略:

**头采样(Head-based)**

- 入口决定整 Trace 是否采,简单
- 1%、10%、动态
- 缺点:错误请求采到的概率低

**尾采样(Tail-based)**

- 整 Trace 完成后再决定
- 错误 / 慢请求 100% 采
- 正常请求降采到 1%
- OTel Collector 支持

**关键 Trace 强制采样**

- 用户 setUser 中标记 VIP
- 关键业务路径(支付)100%

## 部署架构

**典型架构**

```
应用 SDK → OTel Collector(集群)→ Jaeger / Tempo / Datadog
              ├─ 批处理
              ├─ 采样
              ├─ 富化(加 K8s 标签)
              └─ 多后端导出
```

OTel Collector 是关键中间层,解耦应用与后端。

## 局限

- **跨异步消息追踪难**:Kafka 消息要手动注入 Trace ID
- **批处理任务追踪复杂**:批量处理 1000 个消息一条 Trace?N 条 Trace?
- **数据库内部不可见**:能看到"花 500ms 查询",看不到 SQL 计划
- **过度埋点性能损耗**:每 Span 5-50us,高 QPS 服务影响明显
- **学习曲线**:概念多(Span / Trace / Baggage / SpanContext)

## 实践经验

**1. 默认开启自动 instrumentation**

主流框架(Express、FastAPI、Spring Boot、Django)都有自动埋点,装 OTel SDK 即可工作。

**2. 业务关键路径加自定义 Span**

支付、订单、登录等关键路径手动加 Span,标识业务含义。

**3. Tag 设计**

- service.name、service.version(必)
- user.id、tenant.id(根据隐私决定)
- http.method、http.status_code、http.url(自动)
- db.statement(注意 PII 与 SQL 注入风险)

**4. 与日志关联**

每条日志带上 trace_id,即可在日志中跳转到 Trace UI。

**5. 与错误监控关联**

Sentry / Bugsnag 中错误 Issue 嵌入 Trace 链接,看堆栈即看完整请求链路。

## 和其他概念的关系

分布式追踪是 [[可观测性三支柱]] 与 [[微服务]] 时代的关键基础设施。它与 [[Grafana]]、[[Prometheus]]、[[ELK Stack]] 等共同构成 SRE 工具链。

OpenTelemetry 的统一标准让 [[服务网格]](Istio / Linkerd)能自动注入 Trace,与应用代码协同。Sidecar 代理产生的 Span 与应用 Span 拼接为完整 Trace。

它的"上下文传递"思想与 [[Cookie与Session]]、[[JWT]] 等机制同构——都是让"无状态请求"携带状态的工程方案。在 [[AI Agent]] 系统中,把每一步 LLM 调用、工具调用作为 Span,可视化整个 Agent 推理链已成为新范式。
