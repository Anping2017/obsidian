# B+ 树 B+ Tree

## 定义

**B+ 树**是 B 树的变体,为**磁盘存储**优化的多路平衡[[树]]:
- 每个节点可有 m 个键(m 通常几十到几百,与磁盘页大小匹配)
- **所有数据只存于叶子节点**,内部节点只作索引
- **叶子节点之间用链表串起**,支持高效顺序范围扫描

它是 [[关系型数据库]](MySQL InnoDB、PostgreSQL、Oracle)、文件系统(NTFS、ReiserFS、XFS、ext4 目录索引)的事实标准索引结构。

## 核心要点

### 设计动机:磁盘是慢的

机械磁盘随机 IO 约 10 ms,SSD 0.1 ms,内存 10 ns。差距 5-6 个数量级。
[[二叉搜索树]]虽 O(log₂ n) 但每节点一次 IO,n=1B 时高度 30 → 30 次 IO。
B+ 树高度更低(每节点 200 个键时,n=1B 高度仅 4),IO 次数极少。

### B+ 树性质

- 高度 O(log_m n),m 通常 ≥ 100
- 叶子节点同层(完美平衡)
- 内部节点只存键 + 子节点指针,**不存数据** —— 给一个节点放更多键
- 叶子串链表 —— 范围查询友好

### 操作复杂度

| 操作 | 复杂度 | 说明 |
|---|---|---|
| 查找(等值) | O(log_m n) | 几次 IO |
| 范围扫描 | O(log_m n + k) | k 是结果数 |
| 插入 | O(log_m n) | 满则分裂 |
| 删除 | O(log_m n) | 不足则合并/借 |

### B+ 树 vs B 树

| | B 树 | B+ 树 |
|---|---|---|
| 数据位置 | 内/叶都可 | 仅叶子 |
| 内部节点 | 含数据 | 仅索引 |
| 查询单点 | 可在内部命中 | 必到叶子 |
| 范围查询 | 中序遍历跨多层 | 沿叶子链表 O(k) |
| 节点扇出 | 较小 | 较大(每键 + 指针,无数据) |

工程上 B+ 树范围查询的优势压倒性 → 关系型数据库几乎全用 B+ 树。MongoDB 用 B 树。

### MySQL InnoDB 的索引细节

- **聚簇索引(Clustered Index)**:主键 B+ 树,叶子节点直接存整行数据
- **二级索引(Secondary Index)**:叶子节点存主键值,查询需要"回表"再走聚簇索引一次
- **覆盖索引(Covering Index)**:索引包含 SELECT 所需所有列,不回表
- 主键自增 + 短:让聚簇索引顺序写入、空间紧凑

### 节点大小与磁盘页

B+ 树节点通常对齐到磁盘 / OS 页大小(4 KB - 16 KB)。InnoDB 默认 16 KB 页。每节点能放数百键,使树高 3-4 层即覆盖几十亿行。

### 何时不适合 B+ 树

- 写密集 + 顺序键:LSM 树(LevelDB、RocksDB、Cassandra)更优 —— 顺序追加日志,定期合并
- 大量随机点查 + 等值匹配:[[Hash表]]索引可能更快
- 全文搜索:倒排索引(Lucene、Elasticsearch)
- 时序数据:专用引擎(InfluxDB、TimescaleDB)

### 缓存友好

B+ 树查找过程中,前几层节点几乎一定在内存([[缓存]])中,实际磁盘 IO 只发生在最后 1-2 层。InnoDB Buffer Pool 通常 70-80% 的内存就用于缓存这些节点。

## 和其他概念的关系

B+ 树是[[树]]家族最具工业意义的成员之一,与[[Hash表]]互补:Hash 索引 O(1) 但无序,B+ 树 O(log n) 但保留顺序、支持范围。

它和 LSM 树是现代存储引擎的两大分流:B+ 树读优化,LSM 写优化。
- **B+ 树系**:MySQL、PostgreSQL、Oracle、SQL Server、SQLite
- **LSM 系**:LevelDB、RocksDB、Cassandra、HBase、Bigtable、TiKV

[[操作系统]]文件系统的目录结构(ext4 HTree、XFS、Btrfs)、虚拟内存的多级页表(本质是树)在思想上与 B+ 树一脉相承 —— 都是把"内存映射磁盘"问题转为"树查询"。
