# 微服务架构 Microservices

## 定义

**微服务(Microservices)**是一种软件架构风格:把单体应用拆分为**多个小型、独立、围绕业务能力**的服务,各服务:
- 独立开发、部署、扩展、回滚
- 拥有自己的数据存储
- 通过**轻量级机制**通信(HTTP/[[RESTful API]]、gRPC、[[消息队列]])

由 Martin Fowler、James Lewis 在 2014 年系统化总结,基于 Netflix、Amazon 等先驱实践。它是单体(Monolith)架构在大规模团队/系统下的演进答案。

## 核心要点

### 单体 vs 微服务

| 维度 | 单体 | 微服务 |
|---|---|---|
| 部署 | 一个二进制 | 多个独立部署 |
| 技术栈 | 通常统一 | 各自选择 |
| 扩展 | 整体扩 | 按服务独立扩 |
| 团队 | 共享代码库 | 服务对应小团队 |
| 故障域 | 全局 | 局部 |
| 复杂度 | 业务复杂度 | + 分布式复杂度 |
| 启动成本 | 低 | 高(需 DevOps、监控) |

**经验法则**:从单体起步,业务和团队规模到一定阈值再拆分(Martin Fowler "MonolithFirst")。

### 拆分原则

按**业务领域(DDD 限界上下文)**拆,不按技术层拆。
- 每个服务有清晰的业务边界
- 单一职责
- 数据私有(不共享数据库)
- 通过 API 暴露能力

### 服务间通信

| 方式 | 同步/异步 | 适用 |
|---|---|---|
| REST/HTTP | 同步 | 通用、易调试 |
| gRPC | 同步 | 内部高性能 |
| GraphQL | 同步 | BFF 聚合 |
| [[消息队列]](Kafka/RabbitMQ) | 异步 | 事件驱动、解耦 |
| 事件总线 | 异步 | 通知、广播 |

异步通信是高可用关键 —— 同步链路过长会放大故障(雪崩)。

### 关键支撑组件

- **服务注册与发现**:Consul、Eureka、Nacos、Kubernetes DNS
- **API 网关**:Kong、Apigee、Spring Cloud Gateway。负责认证、限流、路由、聚合
- **配置中心**:Nacos、Apollo、Spring Cloud Config
- **熔断/限流/降级**:Hystrix(已停更)、Resilience4j、Sentinel
- **链路追踪**:Jaeger、Zipkin、OpenTelemetry
- **日志聚合**:ELK / Loki + Grafana
- **监控**:Prometheus + Grafana
- **配置中心 + 灰度发布**:支持金丝雀、蓝绿部署

### 数据一致性挑战

跨服务事务难以 ACID,常用模式:
- **Saga**:把长事务拆成本地事务序列 + 补偿事务
- **TCC(Try-Confirm-Cancel)**:三阶段
- **事件溯源(Event Sourcing) + CQRS**:存事件流,读写模型分离
- **最终一致性**:接受短期不一致,异步补齐
- **幂等设计**:重试不导致重复副作用

### 部署演进

容器化([[Docker容器]]) + 编排([[Kubernetes]])是微服务工业化基础。**Service Mesh**(Istio、Linkerd)把通信关注点(重试、超时、TLS、可观测)从代码下沉到 sidecar 代理。

### 何时不该用微服务

- 团队规模小(< 10 人)
- 业务边界尚未清晰
- 性能极敏感(进程内调用 << RPC)
- 对运维成熟度要求高,组织不准备好就上 = 自寻烦恼

Sam Newman 在《Building Microservices》强调:**微服务是给特定问题的解决方案,不是默认架构**。

### 反模式

- 共享数据库(变相耦合)
- 分布式单体(服务拆开但部署、发布耦合)
- 过度同步链路(A→B→C→D,任一挂全挂)
- 服务粒度过细(纳米服务)
- 不实施可观测性盲飞

## 和其他概念的关系

微服务建立在[[设计原则SOLID]](尤其单一职责)之上,在系统层面延展。它需要[[Docker容器]]、[[Kubernetes]]、CI/CD、可观测性栈作为支撑。[[消息队列]](Kafka)是异步解耦的关键。

[[NoSQL数据库]]在微服务下兴盛 —— 每服务独立选库。[[CAP定理]]、[[ACID事务]]、最终一致性等分布式概念是微服务必备知识。

[[Serverless]]、Service Mesh、API Gateway 都可视为微服务的特定演进或补充。Domain-Driven Design (DDD) 提供拆服务的方法论。

AI 应用:大规模 [[大语言模型]] 服务系统普遍采用微服务架构 —— 把模型推理、向量召回、提示词组装、安全审核、对话状态、计费等拆为独立服务,各自横向扩展;[[AI Agent]] 调用各种外部工具的设计与微服务的服务间通信高度同构,工具描述、工具调用、结果回流的协议化(如 [[MCP协议]])正是微服务接口规范化思想在 AI 场景的延伸。
