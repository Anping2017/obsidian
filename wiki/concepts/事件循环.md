# 事件循环 Event Loop

## 定义

**事件循环(Event Loop)**是一种**单线程异步执行模型**:程序保持一个主线程不断从队列中取任务执行,而 IO、定时器、事件等会在合适时机把回调推入队列。它实现"看似并发"的高吞吐 —— 任何操作都不阻塞主线程。

事件循环是 JavaScript(浏览器、Node.js)、Nginx、Redis、Python asyncio、Erlang BEAM 等系统的并发核心。

## 核心要点

### 浏览器事件循环结构

- **调用栈(Call Stack)**:同步代码执行
- **Web APIs**:浏览器提供(setTimeout、fetch、DOM 事件等),独立于 JS 引擎
- **任务队列(Task Queue / Macrotask Queue)**:setTimeout 回调、IO、UI 事件
- **微任务队列(Microtask Queue)**:Promise.then、queueMicrotask、MutationObserver

### 执行顺序

1. 运行同步代码至栈空
2. 清空所有微任务
3. 执行**一个**宏任务
4. 清空所有微任务
5. 渲染(可能)
6. 回到步骤 3

关键:每个宏任务后**一定**先清空微任务再下一个宏任务。Promise.then 的优先级高于 setTimeout(0)。

### Node.js 事件循环(libuv)

Node 的事件循环更复杂,基于 libuv,**6 个阶段循环**:
1. **timers**:setTimeout、setInterval 到期回调
2. **pending callbacks**:某些系统操作的回调
3. **idle, prepare**:内部
4. **poll**:取新 IO 事件、执行 IO 回调
5. **check**:setImmediate 回调
6. **close callbacks**:close 事件回调

每个阶段间清空 nextTick 队列和 microtask 队列。`process.nextTick` 优先级高于 Promise.then。

### Reactor 模式

事件循环模式的别名是 **Reactor**(被动反应):
- 注册感兴趣的 IO 事件 + 回调
- 通过 `epoll`(Linux)/`kqueue`(BSD)/`IOCP`(Windows)等系统调用让内核监听
- 内核就绪通知 → 执行回调

Nginx、Redis、Netty、Tornado、Vertx 都是 Reactor 模式。

### 单线程的优势与代价

**优势**:
- 无锁,避免数据竞争
- 上下文切换成本低
- 内存占用小,可承载海量连接(C10K → C10M)

**代价**:
- CPU 密集任务会阻塞所有事件,需要 worker 线程或子进程
- 错误处理复杂(回调地狱)
- 不充分利用多核 → Node 用 Cluster、PM2 启多进程,Nginx 多 worker

### 协作式 vs 抢占式调度

事件循环是**协作式**:任务自愿让出(异步等待)主线程才能切换。如果一段同步代码长时间不返回,整个事件循环停滞。
对应**抢占式**(操作系统调度):内核强制切换。
现代 Node 通过 Worker Threads 引入有限抢占能力。

### Promise / async-await 的本质

Promise 是事件循环上的"微任务调度器"。`await` 等价于"暂停函数,把后续放进微任务队列"。代码看起来同步,运行时是事件循环驱动。

## 和其他概念的关系

事件循环是[[并发与并行]]的"协程式并发"代表 —— 单线程协作式调度。它与多线程、Actor 模型、CSP 模型一起构成主流并发方案。

[[操作系统]]通过 epoll/kqueue 提供事件驱动的内核接口;libuv、libevent、Boost.Asio 是用户空间的封装。事件循环依赖[[操作系统]]非阻塞 IO(O_NONBLOCK)和 IO 多路复用。

[[微服务]]的服务网格、API Gateway 大量使用事件循环引擎(Nginx OpenResty、Envoy)以应对海量连接。

[[函数式编程]]中的"Functional Reactive Programming"(FRP、RxJS)把事件循环抽象为"事件流",用 map/filter/merge 操作流。
