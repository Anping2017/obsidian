# 消息队列 Message Queue

## 定义

**消息队列(Message Queue, MQ)**是分布式系统中**异步通信**的中间件:生产者(Producer)把消息投递到队列/主题,消费者(Consumer)从中拉取或被推送处理,生产者与消费者**解耦**、**削峰**、**异步执行**。

它是经典[[队列]]数据结构的工业化、分布式、持久化实现。代表产品:**Apache Kafka、RabbitMQ、Apache RocketMQ、ActiveMQ、AWS SQS、Azure Service Bus、Pulsar**。

## 核心要点

### 三大核心价值

1. **异步解耦**:发送者不必等接收者处理完。下单后异步发短信/积分,主流程更快
2. **流量削峰**:秒杀场景把瞬时百万 QPS 平滑到后端可处理速率
3. **服务解耦**:订单服务发事件,库存/物流/积分各自订阅,新增订阅不影响订单

### 两种主要模型

- **点对点(Queue)**:每条消息只被一个消费者消费(任务分发)
- **发布-订阅(Topic / Pub-Sub)**:每条消息广播给所有订阅者(事件通知)

### 主流产品对比

| | Kafka | RabbitMQ | RocketMQ |
|---|---|---|---|
| 模型 | Topic + Partition | Exchange + Queue | Topic + Queue |
| 吞吐 | 极高(百万 TPS) | 中等(几万 TPS) | 高(十万 TPS) |
| 延迟 | 几毫秒到几十毫秒 | 几毫秒 | 几毫秒 |
| 持久化 | 顺序写日志,极强 | 内存优先,可持久 | 顺序写,强 |
| 顺序保证 | 单 partition 内 | 单 queue 内 | 单 queue 内 |
| 事务 | 支持 | 弱 | 支持 |
| 主用途 | 大数据流、日志、事件溯源 | 业务消息、复杂路由 | 阿里电商场景 |

### 投递语义

- **At Most Once**:可能丢,不会重(性能最好)
- **At Least Once**:不会丢,可能重(主流默认)
- **Exactly Once**:不丢不重(代价高,Kafka 通过事务实现)

业务通常需要**幂等设计**配合 At Least Once:消费者去重(基于 messageId 或业务 key + 去重表)。

### 消息中间件解决的典型问题

- **下单后下游处理**:订单 → MQ → 库存/物流/积分/通知
- **跨系统数据同步**:Binlog → MQ → 搜索引擎/缓存
- **流式分析**:Kafka → Spark Streaming / Flink
- **任务队列**:Celery、Sidekiq 都基于 MQ
- **事件溯源**:把所有状态变更存为事件流

### 设计要点

- **消息幂等**:消费者应能多次消费相同消息而不出错
- **消息顺序**:全局顺序代价高,通常按 key 路由到同一分区/队列保证局部顺序
- **死信队列(DLQ)**:多次失败的消息转 DLQ,人工介入
- **延迟消息**:RabbitMQ 插件、RocketMQ 原生、Kafka 需自定义
- **消息积压**:监控延迟,扩容消费者或 partition

### Kafka 的特殊地位

不只 MQ,更是**分布式日志(Distributed Commit Log)**:
- 顺序追加写,极高写入性能
- 多副本(ISR 机制)+ 分区(Partition)实现高可用与水平扩展
- 消费者维护 offset,可重放历史
- 事件溯源、CDC、流处理等模式的基础设施

### 消息队列 vs RPC

| | RPC | MQ |
|---|---|---|
| 同步/异步 | 同步 | 异步 |
| 耦合 | 紧 | 松 |
| 可靠性 | 失败立刻知道 | 最终送达 |
| 吞吐 | 受限于双方在线 | 高,生产消费独立 |
| 典型场景 | 强一致查询 | 事件、解耦、削峰 |

混合架构常见:同步链路 + 异步事件总线。

## 和其他概念的关系

消息队列是[[微服务]]架构异步通信的核心:服务间通过事件而非直接调用。它实现"事件驱动架构(EDA)"和事件溯源(Event Sourcing) + CQRS。

底层依赖[[队列]]数据结构、磁盘顺序 IO、副本/选主([[操作系统]]、Raft/Paxos)、网络协议。Kafka 还经常作为**数据集成层**(替代点对点 ETL),Confluent 提出"Kafka 是公司的中央神经系统"。

[[缓存]] + MQ + DB 是大型系统三大件。流处理框架(Flink、Spark Structured Streaming)直接在 MQ 之上构建实时分析。
