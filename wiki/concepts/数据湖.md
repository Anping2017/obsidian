# 数据湖

## 定义

**数据湖(Data Lake)** 由 Pentaho CTO James Dixon 在 2010 年提出,核心主张是:**用低成本的对象存储,集中容纳来自全企业的所有数据——结构化、半结构化、非结构化——保持原始格式,按需建模**。

它的核心理念是 **schema-on-read**(读取时定义结构),与 [[数据仓库]] 的 **schema-on-write**(写入时强制结构)形成本质对照。这让数据湖能容纳那些"先存下来,以后再说"的数据——日志、图像、视频、IoT 遥测、爬虫页面——而不需要预先设计表结构。

## 核心要点

### 与数据仓库的对照

| 维度 | 数据湖(Lake) | 数据仓库(Warehouse) |
|---|---|---|
| Schema | Schema-on-read | Schema-on-write |
| 数据类型 | 结构化 / 半 / 非结构化 | 结构化 |
| 存储 | 对象存储(S3 / OSS) | 关系型 / 列式数仓引擎 |
| 成本 | 低($/TB) | 高 |
| 处理 | 批 + 流 + ML | 主要 OLAP |
| 用户 | 数据科学家 / 工程师 | 业务分析师 |
| 灵活度 | 高 | 中 |
| 性能 | 不一定快 | 查询优化好 |
| 治理 | 难(易成沼泽) | 强 |

### 关键技术栈

**存储底座**

- AWS S3、Google Cloud Storage、Azure Blob、阿里云 OSS、Hadoop HDFS(早期)

**文件格式**

- 行式:CSV、JSON、Avro
- **列式**:Parquet、ORC ——现代数据湖主流,压缩高、查询快,见 [[列式存储]]

**元数据**

- Hive Metastore、AWS Glue Catalog、Unity Catalog
- 没有元数据,数据湖就是文件堆

**计算引擎**

- 批:[[Apache Spark]]、Presto/Trino、Hive
- 流:[[Apache Flink]]、Kafka Streams
- 交互式查询:Trino、Athena、StarRocks

### 数据湖仓(Lakehouse)

2020 年起,Delta Lake / Apache Iceberg / Apache Hudi 三个开源表格式让数据湖具备:

- **ACID 事务**(对照 [[ACID]])
- **Schema 演进与强制**
- **Time Travel**(查询历史版本)
- **Upsert / Delete**(传统湖只能追加)
- **小文件合并**

数据湖 + ACID = **湖仓一体**,见 [[Lakehouse架构]]。这是过去 5 年大数据架构最重要的演进——数据湖从"半成品"变成与数仓比肩的存储底座。

### 分层模式(Medallion Architecture)

Databricks 提倡的三层湖仓组织:

- **Bronze**:原始数据原样落地
- **Silver**:清洗、去重、连接后的中间表
- **Gold**:面向业务主题的聚合表,供 BI 与 ML 消费

### 数据沼泽(Data Swamp)风险

数据湖最大反面教材是**数据沼泽**——没有元数据、没有质量管控、没有访问控制、没人知道哪条数据可用。Gartner 数据显示,失败的数据湖项目大都死于治理缺位,而非技术问题。

## 典型应用 / 主要厂商

- **集中数据底座**:全企业数据"一湖收纳",上层做 BI、ML、AI
- **机器学习训练数据**:图像、语音、文本原始素材集中存放
- **历史归档**:OLTP 库归档到湖,节省主库压力
- **数据科学探索**:科学家直接查询原始数据,无需 DBA 建模
- **代表平台**:Databricks Lakehouse、AWS Lake Formation、Snowflake、Azure Synapse、阿里云 DLF、华为 LakeFormation

## 局限与陷阱

- **治理是头号难题**:元数据、血缘、权限、质量任一缺位就成沼泽
- **查询性能**:未优化的湖查询比数仓慢一个数量级
- **小文件问题**:海量小 Parquet 拖垮 NameNode / 元数据服务,需定期合并
- **一致性弱**:传统湖只追加,无 ACID,湖仓表格式才补上
- **技能门槛**:工程师需懂存储 + 文件格式 + 计算引擎,跨度大
- **不是 OLTP 替代**:湖不适合事务性写入与点查询
- **"先存再说"易失控**:无业务驱动的数据收集只会徒增成本

## 与其他概念的关系

- 与 [[数据仓库]] 形成 schema-on-read vs schema-on-write 的根本对照
- 现代演进路径:数据湖 → [[Lakehouse架构]](Delta / Iceberg / Hudi)
- 计算层依赖 [[Apache Spark]]、[[Apache Flink]] 等引擎
- 数据通过 [[ETL与ELT]] 或 [[Apache Kafka]] CDC 流入
- 文件存储底座采用 [[列式存储]] 格式(Parquet / ORC)
- 与 [[OLAP vs OLTP]] 中的 OLAP 场景重叠,但定位更宽
- 作为 ML / AI 训练数据底座,服务 [[机器学习]] / [[大语言模型]] 管道
- 与 [[批处理]] / [[流处理]] 共同构成现代数据平台
- 治理可类比 [[公地悲剧]] —— 缺少规则就退化
