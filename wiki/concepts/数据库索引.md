# 数据库索引

## 定义

**索引(Index)** 是数据库为加速查询而维护的辅助数据结构。逻辑上像书的目录,通过额外存储排序后的键和指向行的指针,把扫描全表的 O(n) 操作降到 O(log n)(树索引)或 O(1)(哈希索引)。索引是数据库性能优化的第一手段,但代价是写入变慢、占用磁盘空间。

## 核心要点

- **按数据结构分类**
  - **B+树索引**:主流关系数据库默认,有序、范围查询友好,见 [[B+树]]
  - **Hash 索引**:O(1) 等值查询,不支持范围、排序;Memory 引擎、Redis 内部使用,见 [[Hash表]]
  - **LSM 索引**:写优化,见 [[LSM树]],RocksDB/Cassandra 使用
  - **倒排索引(Inverted Index)**:全文搜索引擎核心,词 → 文档列表;Elasticsearch、Lucene
  - **位图索引(Bitmap)**:每个值一个位向量,基数低的列(性别、状态)极省空间;Oracle、ClickHouse
  - **R 树**:空间数据(地理坐标、矩形)索引;PostGIS
  - **GIN/GiST**:PostgreSQL 通用倒排/广义搜索索引,支持数组、JSON、全文
- **按物理结构分类**
  - **聚簇索引(Clustered Index)**:索引和数据在一起,叶子节点就是行;InnoDB 主键索引
  - **非聚簇索引(Secondary Index)**:叶子节点存主键,需"回表"找行
  - **覆盖索引(Covering Index)**:查询所需列全在索引里,无需回表,极快
- **按列数分类**
  - **单列索引**:CREATE INDEX idx_name ON t(col)
  - **联合索引(Composite)**:CREATE INDEX idx ON t(a, b, c),遵守**最左前缀原则**:WHERE a=? 和 a=? AND b=? 都能用,但单独 WHERE b=? 不能用
- **按唯一性分类**
  - **唯一索引(UNIQUE)**:键不允许重复,创建时检查
  - **主键索引(PRIMARY)**:特殊唯一索引,且非空
  - **普通索引**:键可重复
- **索引失效场景**(查询优化必知)
  - 对索引列做函数运算:WHERE YEAR(created)=2026 不走索引,改 WHERE created BETWEEN ...
  - 隐式类型转换:WHERE phone='123' 但 phone 是 INT,转换后失效
  - 前导模糊:WHERE name LIKE '%abc' 不走 B+树
  - OR 连接非索引列
  - 联合索引违反最左前缀
- **创建索引的原则**
  - 高频查询的 WHERE、JOIN、ORDER BY、GROUP BY 列
  - 区分度高的列(唯一值多)优先
  - 避免对频繁更新的列建索引
  - 索引数量 ≤ 5,过多则写入拖慢、优化器选择困难

## 和其他概念的关系

索引的底层数据结构来自 [[数据结构]] 经典:[[B+树]] 是主流、[[Hash表]] 用于等值、[[跳表]] 在 Redis 替代 B 树。[[LSM树]] 是另一种索引哲学。

索引选择是 [[查询优化器]] 的核心决策:基于代价的优化器(CBO)用统计信息估算每种索引方案的开销,选最优执行计划。

[[关系型数据库]] 普遍依赖索引提升 [[ACID事务]] 中的查询性能;[[NoSQL数据库]] 中 MongoDB 同样靠 B 树索引、Cassandra 靠 LSM 内置索引、Elasticsearch 靠倒排索引。

[[慢查询优化]] 第一步几乎总是分析索引使用情况(EXPLAIN/查询计划)。[[复杂度分析]] 是理解索引价值的理论基础。
