# 服务网格

## 定义

**服务网格(Service Mesh)** 是分布式系统中专门处理服务间通信(东西流量)的基础设施层。它通过在每个服务实例旁部署一个**代理(sidecar proxy)**,透明拦截所有进出流量,把负载均衡、熔断、重试、加密、监控、追踪等"通信治理"能力从应用代码中剥离,下沉到基础设施。代表实现:Istio、Linkerd、Consul Connect、AWS App Mesh。

## 核心要点

- **架构**
  - **数据面(Data Plane)**:每服务实例一个 sidecar 代理(通常是 Envoy / Linkerd-proxy)
  - **控制面(Control Plane)**:配置下发、证书管理、策略推送(Istio 的 istiod)
  - **应用流量被透明拦截**:Pod 内应用 ↔ sidecar ↔ 网络 ↔ 对方 sidecar ↔ 对方应用
- **解决的问题**
  - 微服务通信的横切关注点(可靠性、安全、可观测)在每语言重复实现成本高
  - 代码改一次,业务发布一次,治理能力升级慢
  - 服务网格把这些下沉到基础设施,**应用代码无感**
- **核心能力**
  - **流量管理**
    - [[负载均衡]]:Round Robin / Least Conn / Consistent Hash
    - 路由规则:按 Header / Cookie / 权重路由
    - 灰度发布、金丝雀、AB 测试,见 [[灰度发布与蓝绿部署]]
    - 流量复制(Mirror / Shadow)
  - **韧性**
    - 重试、超时、[[熔断与降级]]
    - 故障注入(Chaos Engineering)
    - [[限流]]
  - **安全**
    - **mTLS 透明加密**(默认开):服务间通信自动加密 + 双向认证,见 [[TLS]]
    - 基于身份的授权(RBAC / ABAC)
    - 证书自动轮换
  - **可观测性**
    - 自动产生指标(请求数、延迟、错误率),见 [[Prometheus]]
    - 自动产生追踪 span,见 [[OpenTelemetry]]
    - 访问日志
    - 拓扑可视化
- **代表实现对比**

| 维度 | Istio | Linkerd | Consul Connect |
|---|---|---|---|
| 数据面 | Envoy(C++) | linkerd2-proxy(Rust) | Envoy |
| 资源占用 | 高 | 极低 | 中 |
| 功能 | 极丰富 | 精简 | 中 |
| 学习曲线 | 陡 | 易 | 中 |
| 出品 | Google + IBM | Buoyant | HashiCorp |

- **xDS 协议**
  - Envoy 的服务发现协议(Listener/Cluster/Endpoint/Route Discovery)
  - 已成事实标准,gRPC、Linkerd、AWS App Mesh 都支持
- **Sidecar 模式 vs Sidecarless**
  - **传统 Sidecar**:每 Pod 一个代理,资源开销叠加
  - **Sidecarless / Ambient Mesh**(Istio 2022 提出):节点级代理,POD 不再嵌入 sidecar,大幅降资源
  - **Cilium Service Mesh**:用 eBPF 在内核拦截,无需用户态代理
- **服务网格 vs API 网关 vs 反向代理**
  - **API 网关**:北向(外 → 内),客户端 → 服务,见 [[API网关]]
  - **服务网格**:东西向,服务 ↔ 服务
  - **反向代理(Nginx)**:简单转发,不具备服务网格的治理能力
  - 实际:网关 + 网格 组合使用
- **采用建议**
  - **微服务规模 < 10**:不建议网格,K8s Service + 库即可
  - **10-50 服务**:Linkerd 这种轻量网格性价比高
  - **50+ 服务、强治理需求**:Istio
  - **资源受限场景**:Cilium / Ambient Mesh
- **代价**
  - **延迟增加**:每跳多 1 个 sidecar,通常 1-3ms
  - **资源开销**:每 Pod 多 1 个容器(几十 MB 内存)
  - **运维复杂**:控制面 + 数据面 + 配置层级多
  - **故障排查**:多了一层"sidecar 视角",调试需熟悉
- **典型场景**
  - **多语言治理统一**:Java / Go / Python / Node 服务统一治理
  - **零信任安全**:跨可用区 / 跨集群通信全 mTLS
  - **细粒度灰度**:按 Header 路由,实现"按用户标签灰度"
  - **跨集群联邦**:多集群一张服务网格

## 和其他概念的关系

服务网格是 [[微服务]] 通信治理的基础设施,与 [[API网关]] 互补(网关管南北、网格管东西)。

把 [[负载均衡]]、[[熔断与降级]]、[[限流]]、[[服务发现]] 等能力下沉到代理层,应用代码彻底解耦。

依赖 [[TLS]] / mTLS 实现零信任。生成的指标 / 追踪通过 [[OpenTelemetry]] 上送到 [[Prometheus]] 等后端,是 [[可观测性三支柱]] 的天然采集层。

[[Kubernetes]] 是服务网格的主要运行环境,Istio / Linkerd 都基于 K8s 部署。

[[灰度发布与蓝绿部署]] 在服务网格上实现极其灵活,按权重 / Header / 用户特征路由。
