# 上下文窗口

## 定义

**上下文窗口(Context Window)** 是 [[大语言模型]] 一次推理调用能处理的最大输入 + 输出 [[Token]] 数。它决定了模型能同时"看见"多少历史对话、文档、代码或工具响应,是 LLM 在工程上最直接的能力维度之一。

历史演进:GPT-2 的 1024 → GPT-3 的 2048 → GPT-4 的 8K/32K → Claude 3 的 200K → Gemini 1.5 与 Claude 现代版本的 1M-2M token。

## 核心要点

**为何上下文窗口受限**

- [[自注意力机制]] 的复杂度 $O(n^2)$ 关于序列长度,显存与时间随 $n^2$ 增长
- [[位置编码]] 训练时见过的最大长度限制了外推能力
- KV Cache 大小线性增长,长上下文推理对显存吃紧

**扩展上下文的关键技术**

| 方向 | 思路 | 代表 |
|---|---|---|
| 更好的位置编码 | RoPE、ALiBi、YaRN 提升外推 | Llama 系列 |
| 高效注意力 | FlashAttention、稀疏注意力 | 工业界普遍采用 |
| Ring/分块注意力 | 把长序列分块跨设备并行 | Gemini 1.5 |
| 状态压缩 / Memory | 把旧上下文压成摘要或外部记忆 | MemGPT、各类 Agent |

**长上下文 != 更好用**

- "中间遗失(Lost in the Middle)":模型对开头结尾信息利用率高,中间部分常被忽略
- 同 token 数下,关键信息**位置**对答案准确度有重大影响
- 长上下文会显著增加成本和延迟,需权衡;[[Prompt Caching]] 可缓解

**与 [[RAG]] 的关系**

- 替代关系:上下文够长时可直接塞入文档,而非靠检索
- 互补关系:超大文档库不可能全塞入,仍需 [[RAG]] 召回
- 工程趋势:百万级上下文 + 检索混合是主流做法

## 和其他概念的关系

- 直接限制因素:[[Token]] 计数与 [[位置编码]] 外推能力
- 实现机制:[[自注意力机制]] 的 $O(n^2)$ 是核心瓶颈
- 经济维度:与 [[Prompt Caching]] 共同决定长 prompt 成本
- 替代或补充:[[RAG]] 在超大语料场景下不可替代
- 关键服务:[[AI Agent]] 长任务、长对话依赖大上下文
