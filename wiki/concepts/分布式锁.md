# 分布式锁

## 定义

**分布式锁(Distributed Lock)** 是在多节点共享资源场景中,通过外部协调服务(Redis、ZooKeeper、etcd、数据库)实现互斥访问的机制。当任务跨节点、跨进程执行时,单机的 [[数据库锁机制]] 不再适用,需要分布式锁保证临界区只有一个执行者。是订单去重、定时任务、库存扣减等场景的基础。

## 核心要点

- **基本要求**
  - **互斥性**:同一时刻只一个客户端持有
  - **可重入(可选)**:同客户端可重复获取
  - **死锁防护**:持有方崩溃后锁能自动释放
  - **容错**:锁服务部分节点故障时仍可用
- **基于 Redis 的实现**
  - **简单 SETNX**
    - `SET key value NX EX 30`:不存在才设置,30 秒过期
    - 客户端释放时:Lua 脚本检查 value 匹配再 DEL(避免误删别人的锁)
    - **风险**:单点故障、主从切换丢锁、超时未续约导致并发执行
  - **Redlock(Redis 官方多实例算法)**
    - 客户端依次向 N 个独立 Redis 实例(通常 5 个)申请锁
    - 多数派(N/2+1)成功且总耗时 < 锁有效期则成功
    - 释放时向所有实例发释放
    - **争议**:Martin Kleppmann 质疑 Redlock 在网络分区+时钟漂移下不安全(著名 Redlock 之争)
    - **改进**:配合 fencing token(单调递增编号,资源服务校验)
- **基于 ZooKeeper 的实现**
  - 创建临时顺序节点(EPHEMERAL_SEQUENTIAL)
  - 编号最小的节点是锁持有者
  - 其他客户端 watch 前一节点,前节点删除则尝试获取
  - **优势**:基于 Zab(Paxos 类),强一致;客户端崩溃时临时节点自动删除
  - **劣势**:性能不如 Redis(强一致代价)
- **基于 etcd 的实现**
  - etcd v3 的 Lease + Compare-And-Swap(CAS)
  - clientv3.NewMutex 封装了完整逻辑
  - Lease 自动续约,客户端失联后租约到期自动释放
  - **优势**:基于 [[Raft共识算法]],一致性强;有租约 TTL
- **基于数据库的实现**
  - **唯一索引**:INSERT 一条 (resource, owner) 记录,失败则锁已被占
  - **行锁 + SELECT FOR UPDATE**:适合短临界区
  - **乐观锁(版本号)**:UPDATE ... WHERE version=?,失败重试
  - **优劣**:简单但性能差,大并发下数据库压力大
- **关键问题与坑**
  - **锁过期但任务未完成**:任务在执行,锁已被别人拿,出现并发
    - 解决:**看门狗(Watchdog)** 自动续约(Redisson 默认机制)
  - **客户端 GC 暂停**:JVM Full GC 导致进程暂停超过锁有效期,业务以为还持有
    - 解决:**fencing token** 资源服务端校验单调递增编号,旧 token 拒绝
  - **网络分区**:Redlock 有此风险,严格场景用 ZK / etcd
  - **死锁**:必须设过期时间,且锁的释放幂等
- **公平 vs 非公平**
  - **非公平锁**:谁先抢到谁拿,饥饿可能
  - **公平锁**:按申请顺序,ZK 顺序节点天然公平
- **锁粒度选择**
  - 全局锁:简单但并发差
  - 资源级锁:按 user_id / order_id 分桶,提升并发
- **替代方案:乐观控制**
  - 很多分布式锁场景可用幂等 + 版本号 + 重试替代
  - 见 [[幂等性]],数据库 INSERT 唯一键、CAS 等

## 和其他概念的关系

分布式锁是单机 [[数据库锁机制]] 在跨节点场景的延伸。它依赖底层强一致的协调服务([[Raft共识算法]] 实现的 etcd / Zab 实现的 ZooKeeper),触及 [[CAP定理]] 的 CP 选择。

[[Quorum]] 协议是 Redlock 的基础(N/2+1 多数派)。

[[幂等性]] 设计常常使分布式锁不必要:写入幂等可以放心重试,无需独占。

在 [[微服务]] 中,定时任务跨实例调度、订单去重、热点资源(秒杀库存)更新都依赖分布式锁。但设计上应优先考虑去掉锁(幂等 + 异步队列)。

[[分布式事务]] 中的协调者也需要分布式锁防止并发协调冲突。
