# 文件名

## 定义

**文件名**(Filename)是文件系统中识别文件的字符串标识。在不同语境中:

- **技术层**:操作系统/文件系统中的字符序列,受编码、长度、字符集限制
- **认知层**:人类辨识文件的视觉标识,影响检索与回忆速度
- **PKM 层**:笔记的"标题—文件名"双重身份,在 Obsidian 等工具中决定 [[wikilink]] 解析

在 Obsidian vault 中,文件名通常等同于笔记的 `title`,也是 wikilink `[[文件名]]` 的目标。

## 核心要点

### 技术约束

| 维度 | 限制 |
|---|---|
| **长度** | NTFS/APFS/ext4 通常 255 字节 |
| **保留字符** | Windows 禁用 `\ / : * ? " < > \|` |
| **保留名** | Windows: CON、PRN、AUX、NUL、COM1-9、LPT1-9 |
| **大小写** | NTFS/exFAT 不区分,APFS/ext4 区分 |
| **编码** | UTF-8 是现代标准,但跨平台同步要小心 |
| **空格** | 技术允许,但脚本/CLI 处理需引号 |
| **首字符** | 多数系统避免点 `.`(隐藏)、空格、连字符 |

### 命名规范常见做法

#### 1. snake_case(下划线)
`my_long_filename.md`
- 优点:CLI 友好,可读
- 缺点:与变量风格冲突

#### 2. kebab-case(连字符)
`my-long-filename.md`
- 优点:URL/Web 友好
- 缺点:CLI 中破折号易被解析为参数

#### 3. CamelCase
`MyLongFilename.md`
- 优点:紧凑
- 缺点:多词阅读难

#### 4. 中文直接命名
`奥卡姆剃刀.md`
- 优点:认知零摩擦,Obsidian wikilink 友好
- 缺点:URL 编码、跨平台编码问题、CLI 操作不便

#### 5. 日期前缀
`2026-05-10-meeting-notes.md`
- 优点:时间排序,Zettelkasten 友好
- 缺点:文件名长

#### 6. ID + 标题
`202605101230-奥卡姆剃刀.md`
- 优点:稳定 ID 不变,标题可改
- 缺点:可读性下降

### Obsidian vault 中的命名建议

本 vault 在 [[CLAUDE.md]] 与 [[SCHEMA.md]] 约定:
- **概念**:`wiki/concepts/<中文名>.md`,文件名 = title
- **实体**:`wiki/entities/<中文名>.md`
- **主题**:`wiki/topics/<中文名>.md`
- **wikilink**:`[[中文名]]`,无 alias
- **避免**:相对路径、英文别名、目录嵌套层级超过 3 层

### 命名的认知影响

- **检索性**:好的文件名是"未来自己"的关键词
- **可发现性**:Obsidian backlinks 通过文件名匹配
- **稳定性**:重命名会破坏外部引用(除非工具自动追踪)
- **唯一性**:同名文件冲突时 Obsidian 会以路径区分

### 与中文名的特殊议题

详见 [[中文名]]。中文文件名:
- 在大多数现代系统(macOS、Windows 10+、Linux UTF-8)运行良好
- 通过 git 同步需要注意 `core.quotePath` 配置
- 通过 URL 共享需要 percent-encoding
- 在终端某些工具下显示为 `\xxx` 编码序列

## 应用场景

- **PKM**:Obsidian、Zettelkasten 的笔记命名
- **代码项目**:模块、组件、配置文件
- **数据资产**:版本化数据集、模型 checkpoint
- **媒体管理**:照片、视频按"日期-地点-主题"
- **文档协作**:Google Drive、Notion 中跨语言团队

## 局限与陷阱

| 陷阱 | 描述 |
|---|---|
| **过长** | 反而难以扫描 |
| **过短** | 缩写一年后自己看不懂 |
| **特殊字符** | 跨平台同步可能损坏 |
| **大小写陷阱** | macOS APFS 与 Linux ext4 行为不同 |
| **重命名连锁** | 引用未自动更新导致死链 |
| **同名歧义** | 没有路径前缀难区分 |
