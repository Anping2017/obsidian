# 事件驱动架构

## 定义

**事件驱动架构(Event-Driven Architecture, EDA)** 是一种以**事件(Event)** 作为系统组件间通信核心范式的架构风格。组件不通过同步 RPC 直接调用对方,而是:

- **生产者(Producer)** 发布事件到事件总线
- **消费者(Consumer)** 订阅感兴趣的事件并异步处理
- 二者通过事件契约解耦,**互不知道对方存在**

事件天然是**过去时**——"OrderPlaced"、"PaymentSucceeded"、"UserSignedUp"——描述"某事已经发生",而不是"请你做某事"。这一时态差异是 EDA 与请求/响应模式最本质的分野。

## 核心要点

### 与请求/响应的对比

| 维度 | 请求/响应(同步) | 事件驱动(异步) |
|---|---|---|
| 时态 | 命令式(Do X) | 陈述式(X happened) |
| 耦合 | 强(知道对方地址) | 弱(只关心事件) |
| 时序 | 即时 | 最终 |
| 失败处理 | 调用方处理 | 重试 / 死信 / 补偿 |
| 一致性 | 强一致 | 最终一致 |
| 可扩展 | 受限 | 高 |
| 调试 | 容易(调用栈) | 难(异步分散) |

### 三种典型模式

**事件通知(Event Notification)**

最轻量。"用户下单了,请关注。" 消费者收到后自行拉取详情。

**事件携带状态转移(Event-Carried State Transfer)**

事件携带完整状态。消费者无需回查生产者,自己维护本地副本。

**事件溯源(Event Sourcing)**

不存当前状态,只存所有事件;通过重放事件得到任意时点状态。见 [[事件溯源]]。

### 关键基础设施

- **事件总线 / 消息中间件**:[[Apache Kafka]](事实标准)、RabbitMQ、AWS EventBridge、Google Pub/Sub
- **流处理引擎**:[[Apache Flink]]、Kafka Streams、Spark Streaming
- **Schema 管理**:Avro / Protobuf + Schema Registry,保证事件契约演进
- **死信队列(DLQ)**:不可处理的事件归档,避免阻塞主流程

### 设计原则

- **事件不可变**:发布即历史,不允许修改
- **事件自包含**:消费者能仅凭事件做出判断,不依赖额外查询
- **幂等消费**:同一事件被消费多次结果一致(消息中间件多为 at-least-once)
- **顺序粒度**:全局有序代价高,通常用 partition key 保证局部有序
- **背压(Backpressure)**:消费速度跟不上时主动减速,而非崩溃

### 与微服务的关系

[[微服务]] 解决"功能拆分",EDA 解决"服务通信"。二者结合催生**事件驱动微服务**——服务之间不直接 RPC,而是发布/订阅事件,实现真正解耦。

### 与 CQRS、Saga 的协同

- **CQRS**:命令端写事件,查询端订阅事件构建读模型
- **[[Saga模式]]**:跨服务事务通过补偿事件序列实现
- **[[Outbox模式]]**:解决"业务写库 + 发事件"的原子性
- 这一组合是分布式系统最终一致性的标准武器

## 典型应用 / 主要厂商

- **电商**:订单 → 支付 → 库存 → 物流,全程事件串联(Amazon、阿里、京东)
- **金融**:每笔交易一个事件,Flink 实时风控
- **物联网**:百万设备状态事件汇聚
- **用户行为分析**:每次点击一个事件,实时画像
- **流式 ETL**:CDC 把数据库变更转事件,实时入仓
- **代表平台**:Confluent、AWS EventBridge、Azure Event Grid、阿里云 EventBridge

## 局限与陷阱

- **调试困难**:异步事件链难追踪,需 [[分布式追踪]]
- **顺序与幂等**:消费者必须设计为幂等,且对乱序鲁棒
- **最终一致代价**:UI 不能立刻看到结果时需要"乐观更新 + 校正"
- **Schema 演进**:事件契约破坏会影响所有消费者,需要严格版本化
- **过度设计**:简单 CRUD 强行事件化只会增加复杂度
- **事件膨胀**:无节制发布事件 → Kafka 主题爆炸 → 治理失控
- **"事件意大利面"**:消费者之间形成隐式调用链,理解成本高

## 与其他概念的关系

- [[Apache Kafka]] 是 EDA 最主流的事件总线
- 流处理引擎([[Apache Flink]]、Kafka Streams)是事件的实时计算者
- 与 [[微服务]] 是天然搭档,共同构成现代分布式系统
- 与 [[CQRS]]、[[事件溯源]]、[[Saga模式]]、[[Outbox模式]] 形成模式集合
- [[Kappa架构]] 是 EDA 在数据管道层面的具象
- 异步特性需要 [[分布式追踪]] / [[OpenTelemetry]] 保证可观测
- 与 [[服务网格|Service Mesh]] 形成对照:网格管同步 RPC,EDA 管异步事件
- 一致性退化为 [[BASE理论]] 而非 [[ACID事务]]
