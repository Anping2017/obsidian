# 分库分表

## 定义

**分库分表(Sharding)** 是把单一数据库的数据按规则拆分到多个数据库实例或表中,以突破单机的存储、并发、性能上限。是 [[关系型数据库]] 在数据规模 / QPS 超过单机能力时的标准水平扩展方案。

## 核心要点

- **拆分维度**
  - **垂直拆分(Vertical Split)**
    - **垂直分库**:按业务模块拆库,如用户库、订单库、商品库
    - **垂直分表**:按列拆,把大字段(blob/text)单独成表,提升主表性能
  - **水平拆分(Horizontal Split / Sharding)**
    - **水平分表**:按行拆,如按 user_id % 16 拆 16 张表,放在同库
    - **水平分库**:同样按行拆,放到不同库,真正水平扩展
- **拆分键(Sharding Key)选择**
  - 选择最频繁查询的字段(用户 ID、订单 ID)
  - 高基数、分布均匀(避免热点)
  - 选错代价巨大,因为重新分片成本极高
- **分片策略**
  - **范围分片(Range)**:按时间或 ID 范围,易做冷热分离,但易热点
  - **哈希分片(Hash)**:hash(key) % N,均匀但范围查询要扫所有分片
  - **一致性 Hash**:见 [[一致性Hash]],节点增减最小化数据迁移
  - **目录/查找表**:维护 key → shard 映射,灵活但需额外服务
- **核心挑战**
  - **跨分片 JOIN**:从前端 / 中间件层做 JOIN,或冗余字段避免 JOIN
  - **跨分片事务**:见 [[分布式事务]],需要 2PC/TCC/Saga
  - **跨分片聚合**:COUNT/GROUP BY 需各分片算 + 合并(MapReduce 思想)
  - **跨分片排序与分页**:深翻页性能差,需分片排序后归并
  - **全局唯一 ID**:不能用自增,需 UUID / 雪花 ID(Snowflake)/ 号段服务
- **重新分片(Resharding)**
  - 业务发展超出原分片容量时不得不做
  - 双写 + 灰度切流 + 校验 + 切换,极其复杂
  - 一致性 Hash 可大幅降低迁移量
- **典型架构**
  - **客户端分片**:应用直连各分片库(Sharding-JDBC、ShardingSphere-JDBC)
  - **代理分片**:中间件层(MyCat、ShardingSphere-Proxy、Vitess、ProxySQL)
  - **数据库自分片**:TiDB、CockroachDB、Spanner 原生支持,对应用透明
- **分库分表 vs 分布式数据库**
  - 传统分库分表:应用承担复杂性
  - NewSQL(TiDB/CockroachDB):底层自动分片 + Raft + 全局事务,应用看到的还是单库
  - 选择视团队能力与改造成本

## 和其他概念的关系

分库分表是 [[关系型数据库]] 突破单机瓶颈的传统方案。其挑战大多在 [[分布式事务]]、[[分布式锁]]、跨分片 JOIN 上。

[[一致性Hash]] 是分片策略的常用算法,降低重新分片的迁移量。

在 [[微服务]] 架构下,数据库 per service 已经做了垂直拆分,大业务还需进一步水平分片。

NewSQL 数据库(TiDB、CockroachDB)用 [[Raft共识算法]]、[[MVCC]]、分布式 [[事务隔离级别]] 把分片复杂性下沉到数据库层,本质是分库分表的演进。

[[读写分离]] 通常与分库分表配合,主库写、从库读,进一步分担压力。[[缓存]] 层(Redis)是分库分表的搭档,降低分片库的查询压力。
