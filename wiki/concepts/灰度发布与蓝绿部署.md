# 灰度发布与蓝绿部署

## 定义

**部署策略(Deployment Strategy)** 是将新版本服务推上生产的方式。从最朴素的"停机部署"到"金丝雀"、"蓝绿"、"灰度"逐步演化,目的是在**速度、风险、回滚成本**之间取舍。是 CI/CD、SRE 和现代云原生发布管理的核心实践。

## 核心要点

- **常见策略**

| 策略 | 流量切分 | 回滚速度 | 资源占用 | 适用场景 |
|---|---|---|---|---|
| Recreate | 全量替换,先停后起 | 慢 | 1× | 内网工具、低 SLA |
| Rolling Update | 一台台滚 | 中 | 1× | 通用,K8s 默认 |
| Blue-Green | 0% / 100% 切换 | 极快 | 2× | 强 SLA、易回滚 |
| Canary | 1% → 10% → 100% | 快 | 1.x× | 大规模、关键业务 |
| 灰度(Gray Release) | 按用户 / 区域 / 标签 | 快 | 1.x× | 精细化验证 |
| A/B Testing | 对比组 | 不适用 | 1.x× | 产品功能验证 |
| Shadow / Mirror | 流量复制不影响生产 | 不适用 | 2× | 性能 / 兼容性测试 |

- **蓝绿部署(Blue-Green)**
  - **蓝色环境**:当前生产
  - **绿色环境**:新版本,完整副本
  - 部署步骤
    - 1. 在绿色环境部署 + 测试
    - 2. 切换 [[负载均衡]] / DNS,所有流量从蓝 → 绿
    - 3. 蓝色保留作为回滚兜底,稳定后下线
  - **优点**:回滚秒级(切回 LB)、零停机、隔离风险
  - **缺点**:双倍资源、数据库 schema 变更难协调
- **金丝雀(Canary)**
  - **由来**:矿工带金丝雀下井检测有毒气体
  - 步骤
    - 1. 部署一台新版本(canary)
    - 2. 路由 1% 流量到 canary,观察指标
    - 3. 1% → 10% → 50% → 100% 逐步放量
    - 任何指标异常立即回滚
  - **优点**:渐进式、风险可控、不需要双倍资源
  - **缺点**:发布周期长、需精细监控
- **灰度发布(细粒度金丝雀)**
  - 按 **用户、地域、设备、标签、AB 组** 等条件路由
  - 例:先开放给内部员工 → VIP → 北京用户 → 全量
  - 实现:[[API网关]] / [[服务网格]] 按 Header / Cookie 路由
  - **场景**:重大改版、灰度回收用户反馈、精准 AB
- **A/B 测试**
  - 不是部署策略,是产品验证手段
  - 50% 用户走 A 版本、50% 走 B 版本,对比转化率
  - 长期并行运行,基于统计显著性决定胜出
  - 与灰度的区别:灰度的目标是"最终所有人切换",AB 的目标是"选出最优版本"
  - 见 [[AB测试]]
- **影子流量(Shadow / Mirror)**
  - 把生产流量复制一份发给新版本,但响应丢弃
  - 验证新版本的兼容性、性能,不影响真实用户
  - 实现:Envoy mirror、Istio mirror
- **K8s 部署策略**
  - **Rolling Update**:Deployment 默认,maxSurge / maxUnavailable 控制速率
  - **Recreate**:Deployment 配置 strategy.type=Recreate
  - **Blue-Green / Canary**:用 Argo Rollouts、Flagger 等扩展
- **数据库变更协调**
  - **不可向下兼容的 schema**:先扩字段(老版兼容)→ 改代码 → 用新字段 → 删旧字段
  - **三步发布(Expand-Contract)**:数据库变更跨多次部署完成
  - **Feature Toggle**:用开关控制新功能启用,与部署解耦
- **特性开关(Feature Toggle / Flag)**
  - 把"是否启用新功能"做成配置,可不发版即开关
  - 配合灰度按用户标签开关
  - 工具:LaunchDarkly、Unleash、Apollo Config
  - **优势**:发布与开通解耦,A/B 实验高效
  - **代价**:开关增加代码复杂度,需定期清理
- **回滚策略**
  - **快速回滚**:蓝绿切 LB、Canary 把流量打回旧版
  - **数据回滚**:不可逆操作前必须备份;Schema 变更先扩后缩
  - **配置回滚**:配置中心版本管理(Apollo / Nacos)

## 和其他概念的关系

灰度 / 蓝绿是 [[微服务]] 与 [[Kubernetes]] 时代的标准发布姿势,依赖 [[负载均衡]]、[[API网关]]、[[服务网格]] 提供细粒度流量路由。

A/B 测试与 [[AB测试]](已存在概念)是产品验证视角,与灰度是发布视角的姊妹篇。

[[可观测性三支柱]](指标 / 日志 / 追踪)是灰度成败的眼睛:无监控的灰度等于裸奔。

[[幂等性]] 设计支撑发布期间的失败重试。[[熔断与降级]] 在灰度期间保护未推全量的部分。

特性开关是与"持续部署"配合的"持续交付"利器:代码上线但功能默认关闭,业务侧灵活开通。
