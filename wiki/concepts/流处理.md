# 流处理

## 定义

**流处理(Stream Processing)** 是对**无界、持续到达**的数据流进行低延迟连续计算的范式。与 [[批处理]] 处理静态数据相对,流处理在数据产生瞬间消费,延迟从秒到毫秒,是实时风控、监控告警、欺诈检测、动态推荐、实时报表等场景的核心引擎。代表系统:Apache Flink、Kafka Streams、Apache Storm、Spark Structured Streaming。

## 核心要点

- **流处理核心抽象**
  - **流(Stream)**:无界的事件序列
  - **算子(Operator)**:对流做转换(map / filter / aggregate / window)
  - **状态(State)**:跨事件累积的信息(计数、最近 N 个值)
  - **窗口(Window)**:把无界流切成有界片段进行聚合
  - **水印(Watermark)**:时间进度标记,处理乱序与迟到
- **三种时间语义**
  - **事件时间(Event Time)**:事件实际发生的时间(从消息体读取)
  - **摄入时间(Ingestion Time)**:数据进入系统的时间
  - **处理时间(Processing Time)**:算子处理时的墙钟时间
  - 事件时间最准确,需要水印协调;处理时间最简单但跨节点不一致
- **窗口类型**
  - **滚动窗口(Tumbling)**:固定大小、不重叠,如每分钟统计
  - **滑动窗口(Sliding)**:固定大小、重叠移动,如每 10 秒统计过去 1 分钟
  - **会话窗口(Session)**:按事件间隔切窗,如用户连续操作 5 分钟无活动则结束
  - **全局窗口(Global)**:不切,需自定义触发器
- **水印(Watermark)**
  - 标记"事件时间 ≤ T 的数据已到齐(基本上)"
  - 触发窗口计算的依据
  - **迟到数据**:超过水印才到的数据,可丢弃 / 旁路输出 / 重新触发
  - 水印生成策略:固定延迟(如最大 - 5s)、自适应
- **状态管理**
  - **算子内部状态**:计数器、累加和、最近 N 元素
  - **存储后端**:内存、RocksDB(Flink 默认大状态后端)
  - **检查点(Checkpoint)**:定时把状态快照到持久化存储
  - **保存点(Savepoint)**:手动触发,用于版本升级
  - **精确一次语义(Exactly-Once)**:基于检查点 + 事务性输出
- **三大处理保证**
  - **At-most-once**:可能丢,不会重(对延迟极敏感场景)
  - **At-least-once**:不丢可能重(配合 [[幂等性]] 即可)
  - **Exactly-once**:不丢不重(Flink 的两阶段提交 + Kafka 事务)
- **主流引擎对比**
  - **Apache Flink**
    - 真流处理,事件驱动
    - 强大的状态管理 + 精确一次
    - 批流统一(批是有界流)
    - 中文社区最活跃
  - **Kafka Streams**
    - 库而非引擎,直接嵌入 JVM 应用
    - 轻量,不需独立集群
    - 与 Kafka 深度耦合
  - **Apache Spark Structured Streaming**
    - 微批模拟流(batch interval 秒级)
    - 与 Spark 批处理统一 API
    - 延迟高于真流处理
  - **Apache Storm**(过时)
  - **Apache Beam**:统一 API,可在 Flink/Spark/Dataflow 后端运行
- **典型应用**
  - **实时风控**:每笔交易的反欺诈实时打分
  - **运营监控**:网站 PV/UV 实时大盘
  - **物联网**:传感器数据实时聚合告警
  - **推荐系统**:用户行为流式更新特征
  - **CDC 实时同步**:Debezium + Kafka + Flink → 数仓
  - **流式 ETL**:数据从源实时落到 OLAP
- **挑战**
  - **乱序数据**:网络延迟导致后到的事件时间早,水印负责处理
  - **背压(Backpressure)**:下游慢使上游堆积,Flink 自动调整速率
  - **状态膨胀**:无限累积状态需 TTL 清理
  - **故障恢复**:精确一次需要从检查点恢复 + 输出端事务

## 和其他概念的关系

流处理与 [[批处理]] 是大数据计算的两大范式,Flink 和 Spark 都在追求"批流统一"。[[Lambda架构]] 用批+流并行,Kappa 架构主张只用流处理替代批。

流处理离不开 [[消息队列]](Kafka / Pulsar)作为数据骨干,从来源接入到结果输出都通过队列连接。

[[幂等性]] 是流处理 At-least-once 模式的搭档,业务消费幂等就等价于精确一次。

[[一致性Hash]] 是流处理分区的常用手段,保证同 key 数据进同 task。

[[微服务]] 的事件驱动架构(Event-Driven)、CQRS、事件溯源(Event Sourcing)本质都是流处理的应用。

[[可观测性三支柱]] 中,日志和指标的实时聚合通常通过流处理引擎完成。
