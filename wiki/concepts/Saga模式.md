# Saga 模式

## 定义

**Saga 模式** 由 Hector Garcia-Molina 和 Kenneth Salem 在 1987 年的论文《Sagas》提出,后被 [[微服务]] 时代复兴。它解决的核心问题:**当一个业务操作跨多个服务、每个服务有自己数据库时,如何保证整体一致性?**

传统 ACID 事务([[ACID事务]])在分布式场景下不可行——两阶段提交(2PC)会拖死系统、违反服务自治。Saga 提出:**把长事务分解为一组本地事务,每个本地事务有对应的补偿操作,失败时按反向顺序补偿**。

## 经典例子:订单处理

下单流程跨四个服务:
1. **订单服务**:创建订单
2. **库存服务**:扣减库存
3. **支付服务**:扣款
4. **物流服务**:创建发货单

任一步失败,前面已成功的步骤需要"撤销"。

**正向流(Happy Path)**

```
T1: 创建订单
T2: 扣库存
T3: 扣款
T4: 创建发货单
```

**回滚(失败时)**

如果 T3 扣款失败:
```
C2: 恢复库存
C1: 取消订单
```

补偿不是"撤销"(数据库回滚),而是"反向业务操作"——补偿动作是新的本地事务。

## 两种实现方式

**1. 编排式(Orchestration)**

中央协调器(Orchestrator)调度各步骤:

```
Orchestrator → 调订单服务 (T1) → 等成功
            → 调库存服务 (T2) → 等成功
            → 调支付服务 (T3) → 失败
            → 调库存服务补偿 (C2)
            → 调订单服务补偿 (C1)
```

**优点**

- 流程清晰
- 易调试(集中日志)
- 易增删步骤

**缺点**

- 单点协调器
- 协调器复杂度增长

**实现**:
- AWS Step Functions
- Temporal
- Camunda Zeebe
- Spring Cloud / Saga 模式
- 自研协调器

**2. 协同式(Choreography)**

各服务通过事件互相反应,无中央协调:

```
订单服务发出"OrderCreated" 事件
  → 库存服务监听,扣库存,发"StockReserved" 事件
    → 支付服务监听,扣款,发"PaymentSucceeded" 事件
      → 物流服务监听,创建发货单
      → 失败时发 PaymentFailed → 库存监听补偿
```

**优点**

- 无单点
- 服务高度自治
- 与事件驱动架构融合

**缺点**

- 流程隐式,难追踪("分布式 if-else 散在各处")
- 调试困难
- 全局逻辑改动需多服务修改

实现依赖 [[消息队列]](Kafka、RabbitMQ)或事件总线。

## 选择决策

**选编排**

- 流程清晰、步骤多
- 团队偏好显式控制
- 已用 Temporal / Step Functions

**选协同**

- 服务团队独立性强
- 流程少、变化少
- 已大量用事件驱动

实践中混用——核心交易用编排,通知类辅流程用协同。

## 关键设计要点

**1. 补偿操作的幂等性**

补偿可能被多次触发(网络重试),必须幂等:
- 用唯一 ID 去重
- "已补偿"状态标记
- 数学幂等(SET vs DELTA)

**2. 补偿不能失败**

补偿失败 = 系统进入半成功状态。设计上:
- 补偿应是简单的、几乎一定能成功的
- 失败时进入"人工介入"队列
- 补偿之前先冻结资源(可达成补偿前提)

**3. 状态持久化**

每步状态必须落库,否则进程崩溃后恢复困难:
- Saga Log:每步前后写日志
- 中断后从日志恢复

**4. 隔离性弱**

Saga 期间数据可能"半成功"被读到(比如订单已建,库存还没扣)。需:
- 状态字段标识(pending、confirmed、failed)
- 业务规则容忍
- 必要时加业务锁(资源预留)

## Saga vs 2PC vs TCC

| 维度 | 2PC | TCC | Saga |
|---|---|---|---|
| 一致性 | 强 | 强 | 最终 |
| 性能 | 差(阻塞) | 中 | 好 |
| 自治性 | 差(锁住) | 中(预留) | 好 |
| 复杂度 | 协议复杂 | 服务需 Try/Confirm/Cancel | 业务侧补偿 |
| 实战 | 数据库内 / 老旧系统 | 金融 | 互联网主流 |

**TCC(Try-Confirm-Cancel)**

- Try:预留资源(冻结账户金额)
- Confirm:确认(实际扣款)
- Cancel:取消(解冻)

比 Saga 强一致,但服务必须实现三阶段接口,侵入性大。蚂蚁、腾讯等金融业务常用。

## 实战工具

**Temporal**

- Uber 出品(原 Cadence)
- 编排式 Saga 标杆
- 用代码写工作流(JS/Go/Java/Python)
- 自动持久化、重试、状态追踪
- 强大的可视化界面

```typescript
async function bookTrip(input) {
  const flight = await activities.bookFlight(input)
  try {
    const hotel = await activities.bookHotel(input)
    return { flight, hotel }
  } catch (err) {
    await activities.cancelFlight(flight.id)  // 补偿
    throw err
  }
}
```

**AWS Step Functions**

- 状态机 JSON 定义
- 与 AWS 服务深度集成
- Serverless,按用量计费

**Camunda Zeebe / BPMN**

- 业务流程建模(BPMN 2.0)
- 高并发流程引擎

## 案例:Netflix Conductor

Netflix 开源工作流引擎,大规模 Saga 编排:
- 支持 100 万 + 任务/秒
- 任务定义 JSON,工作者用任意语言
- 内置重试、超时、条件、循环

## 反模式

**1. 补偿循环**

补偿失败 → 触发新补偿 → 又失败,无限循环。需熔断。

**2. 长 Saga**

50 步的 Saga 超出可观测性极限。拆为多个子 Saga。

**3. 跨多 Saga 共享状态**

状态污染,难追踪。各 Saga 应自包含。

**4. 补偿不幂等**

重试导致重复扣款 / 重复释放。

## 实战检查清单

- [ ] 每步操作幂等
- [ ] 每步对应的补偿可执行
- [ ] Saga 状态持久化
- [ ] 失败时有明确人工介入流程
- [ ] 补偿期间数据用状态字段隔离
- [ ] 监控:Saga 成功率、补偿率、卡住数
- [ ] Timeout 设置(每步超时即触发补偿)
- [ ] 兼容 At-Least-Once 投递(重复事件)

## 局限

- 隔离性弱(中间状态可能被读)
- 调试复杂(分布式追踪必需)
- 某些操作无法补偿(发邮件已发不能撤回)
- 业务建模复杂度增加
- 补偿设计常被忽视(快乐路径写完就上线)

## 和其他概念的关系

Saga 是 [[微服务]] 跨服务事务的核心模式,与 [[ACID事务]]、[[BASE理论]] 共同构成分布式一致性知识体系。它依赖 [[消息队列]]、[[事件溯源]]、[[CQRS]] 等基础设施实现。

补偿模式与 [[Circuit Breaker]]、[[Outbox模式]] 等弹性模式共同构成可靠分布式系统的工具集。在 [[CQRS]] + [[事件溯源]] 体系中,Saga 自然与事件流融合——事件就是 Saga 步骤的驱动力。

它体现的"接受最终一致 + 业务补偿"哲学是 [[CAP定理]] 在工程层面的实用回应——大多数互联网业务可接受短期不一致换取可用性。
