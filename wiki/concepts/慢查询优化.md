# 慢查询优化

## 定义

**慢查询优化(Slow Query Tuning)** 是定位、分析、改写数据库中执行时间超过阈值的 SQL 的工程实践。慢查询往往是系统延迟、超时、雪崩的源头,是数据库性能工程师的日常工作。

## 核心要点

- **发现慢查询**
  - **慢日志**:MySQL slow_query_log + long_query_time(秒);PostgreSQL log_min_duration_statement
  - **APM 系统**:DataDog、New Relic、阿里云 Insight 实时识别 Top SQL
  - **用户反馈**:页面卡顿、超时报错倒推 SQL
  - **percona-toolkit / pt-query-digest**:聚合慢日志,按指纹排序
- **执行计划分析**
  - MySQL:`EXPLAIN sql` / `EXPLAIN ANALYZE sql`(8.0)
  - PostgreSQL:`EXPLAIN (ANALYZE, BUFFERS) sql`
  - 关键看
    - **type/access path**:ALL(全表) / index / range / ref / eq_ref / const(由差到好)
    - **rows**:估算扫描行数,与实际差异大说明统计过期
    - **Extra**:Using filesort / Using temporary 是警告
    - **Buffers**:实际 IO 次数,反映 buffer pool 效率
  - 见 [[查询优化器]]
- **索引优化**
  - **加索引**:WHERE/JOIN/ORDER BY 列、高基数列
  - **联合索引**:遵循最左前缀,多次单列查询可合并成一个联合索引
  - **覆盖索引**:把 SELECT 列也加进索引,免回表
  - **删冗余索引**:idx(a) 已被 idx(a,b,c) 覆盖,删
  - 见 [[数据库索引]]
- **SQL 改写**
  - **避免 SELECT \***:只取需要的列
  - **限制返回行数**:LIMIT,深度分页用游标(WHERE id > last_id)
  - **EXISTS 替代 IN/COUNT**:存在性判断能提前退出
  - **JOIN 替代相关子查询**
  - **UNION ALL 替代 UNION**:不需要去重时
  - **避免 OR**:改 IN 或 UNION
  - **避免函数/计算在索引列上**:`WHERE DATE(created)=?` → `WHERE created BETWEEN ? AND ?`
- **表设计优化**
  - **选合适字段类型**:INT 比 BIGINT 省一半空间
  - **避免 NULL**:索引、统计、计算都麻烦
  - **冷热分离**:历史数据归档,主表瘦身
  - **垂直拆分**:大字段(text/blob)单独建表
  - 见 [[数据库范式]]、[[分库分表]]
- **统计信息维护**
  - 优化器靠统计选计划,统计过期会选错
  - MySQL:ANALYZE TABLE 手动更新 / 自动更新阈值
  - PostgreSQL:ANALYZE / autovacuum
  - 大表批量 DML 后必须更新
- **参数配置**
  - **innodb_buffer_pool_size**:MySQL 缓冲池,通常设为机器内存的 60%-80%
  - **shared_buffers / effective_cache_size**:PostgreSQL 对应参数
  - **max_connections**:连接数 vs 内存权衡
  - **query_cache**(MySQL,8.0 已废弃):并发下反而成瓶颈
- **架构层优化**
  - **加 [[缓存]]**:Redis 挡热点查询
  - **[[读写分离]]**:从库分担读
  - **[[分库分表]]**:超大表水平拆
  - **异步化**:报表查询走 [[消息队列]] + 离线计算
  - **OLAP 分流**:复杂分析查询走 [[数据仓库]]
- **死锁与锁等待**
  - 见 [[数据库锁机制]]
  - 长事务、热点行更新、缺索引导致的间隙锁扩大都会引发死锁
- **典型反模式**
  - N+1 查询:循环里查数据库,改批量
  - 大事务:拆小事务降低锁持有时长
  - 没分页扫全表:LIMIT 大 OFFSET 仍要扫前面全部
  - 模糊查询前导%:全表扫,改全文索引或 ES

## 和其他概念的关系

慢查询优化围绕 [[查询优化器]] 输出的执行计划展开,涉及 [[数据库索引]] 选择、[[数据库范式]] 设计、[[MVCC]] 与 [[数据库锁机制]] 的并发控制等多方面。

[[读写分离]]、[[分库分表]]、[[缓存]] 是单库优化耗尽后的架构层手段。

在 [[微服务]] 中,慢查询往往拖垮整条链路,需要 [[熔断与降级]] 与 [[限流]] 配合保护。

[[OLAP vs OLTP]] 设计错位是慢查询的根因之一:在 OLTP 库跑分析查询,需要分流到 [[数据仓库]]。
