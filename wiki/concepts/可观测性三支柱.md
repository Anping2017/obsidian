# 可观测性三支柱

## 定义

**可观测性(Observability)** 是从系统的外部输出推断内部状态的能力。Cindy Sridharan 在《Distributed Systems Observability》中明确**日志(Logs)、指标(Metrics)、追踪(Traces)** 三支柱(Three Pillars),分别回答"发生了什么"、"系统状态如何"、"请求经过了哪里",共同支撑 [[微服务]] 与分布式系统的故障定位与性能优化。

## 核心要点

- **日志(Logs)**
  - **是什么**:离散的事件记录,带时间戳和上下文
  - **特征**:结构化(JSON)/ 半结构化 / 文本,信息密度高,体积大
  - **典型用途**:错误堆栈、业务审计、调试
  - **采集**:Fluentd / Filebeat / Logstash / Vector
  - **存储**:ElasticSearch、Loki(成本优化)、ClickHouse
  - **查询**:Kibana、Grafana
  - **挑战**:海量数据成本高,需采样 / 分级 / 归档
  - **结构化日志要点**
    - 用 JSON 而非纯文本
    - 携带 trace_id、user_id、request_id 关联上下文
    - 级别合理(DEBUG/INFO/WARN/ERROR/FATAL)
    - 敏感数据脱敏
- **指标(Metrics)**
  - **是什么**:可聚合的数值时序数据
  - **特征**:数值型,时间序列,体积小,可计算 / 告警
  - **四类指标(Prometheus)**
    - **Counter**:单调递增(请求数、错误数)
    - **Gauge**:可增可减(CPU、内存、连接数)
    - **Histogram**:分桶统计(延迟分布)
    - **Summary**:分位数(P99 延迟)
  - **黄金信号(Google SRE)**:延迟、流量、错误率、饱和度
  - **采集**:Prometheus(pull 模型)、StatsD / Telegraf(push 模型)
  - **存储**:Prometheus、VictoriaMetrics、InfluxDB、Mimir
  - **可视化与告警**:Grafana、Alertmanager
- **追踪(Traces)**
  - **是什么**:一个请求在多服务间传递的完整路径
  - **核心概念**
    - **Trace**:整个调用链,有唯一 trace_id
    - **Span**:链中的一段(单服务调用),有 span_id 和 parent_span_id
    - **Context Propagation**:trace_id 通过 HTTP Header / 消息属性向下游传递
  - **典型用途**:慢请求归因、链路依赖分析、故障定位
  - **实现**:Jaeger、Zipkin、AWS X-Ray、Datadog APM、SkyWalking
  - **协议**:OpenTelemetry(OTel)是统一标准,W3C TraceContext
- **三者关系**
  - **指标快、日志详、追踪联**
  - **指标**:发现异常("错误率涨了")
  - **追踪**:定位异常("订单服务调用支付服务慢")
  - **日志**:解释异常("具体哪个 SQL 报错")
  - 三者关联:指标告警 → 跳转追踪看链路 → 链路 ID 反查日志
- **OpenTelemetry(OTel)**
  - CNCF 项目,合并 OpenTracing + OpenCensus
  - 统一三支柱采集 SDK + 协议(OTLP)
  - 各语言 SDK + Collector + 导出到任意后端
  - 是当代可观测性事实标准
- **APM(Application Performance Management)**
  - 综合三支柱 + 用户体验数据(RUM、Synthetic)
  - 商业产品:Datadog、New Relic、Dynatrace、AppDynamics
  - 中国:阿里云 ARMS、腾讯云 APM
- **eBPF 在可观测性中的兴起**
  - 内核层无侵入采集,延迟与丢包等数据
  - Pixie / Cilium Hubble / Beyla
- **可观测性 vs 监控**
  - **监控(Monitoring)**:已知的关键指标 + 告警(被动响应)
  - **可观测性**:支持探索未知问题(主动调查)
  - 监控是可观测性的子集
- **设计原则**
  - **Cardinality 控制**:指标 label 不要无限增长(user_id 慎做 label)
  - **采样**:Trace 全量代价高,头部采样 / 尾部采样
  - **关联性**:trace_id / request_id 贯穿三支柱
  - **数据生命周期**:不同支柱不同保留期(Metrics 30 天、Logs 7 天、Traces 7 天)

## 和其他概念的关系

可观测性是 [[微服务]] 与分布式系统的"眼睛"。没有可观测性,故障定位会变成大海捞针。

是 [[熔断与降级]]、[[限流]]、[[灰度发布与蓝绿部署]] 决策的依据:无监控的灰度等于裸奔。

[[流处理]] 引擎(Flink / Kafka Streams)经常用于实时聚合指标 → 时序库。

[[API网关]] 与 [[服务网格]] 是可观测性的天然采集点,能在不修改业务代码情况下获得入向 / 服务间流量的全部数据。

[[Kubernetes]] 配合 Prometheus + Grafana + Loki + Tempo 是云原生可观测性的标准栈。
