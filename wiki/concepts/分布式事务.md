# 分布式事务

## 定义

**分布式事务(Distributed Transaction)** 是跨多个数据库实例、多个服务的事务,要保证它们的一组操作要么全部成功要么全部失败。在 [[微服务]]、[[分库分表]] 架构下,跨节点 [[ACID事务]] 不再依靠单库,需要专门的协议或模式。是分布式系统中最棘手的问题之一,各方案在一致性、可用性、复杂度上各有取舍。

## 核心要点

- **强一致协议**
  - **2PC(Two-Phase Commit,两阶段提交)**
    - **Prepare 阶段**:协调者询问所有参与者能否提交,参与者锁资源、写日志、回 YES/NO
    - **Commit 阶段**:全 YES 则发 COMMIT,任一 NO 则发 ROLLBACK
    - **优点**:强一致
    - **缺点**:同步阻塞、协调者单点、参与者长时间持锁、崩溃恢复复杂
    - 实际:XA 协议、MySQL XA、JTA 都是 2PC
  - **3PC(Three-Phase Commit)**
    - 在 2PC 之间加 CanCommit 阶段、引入超时
    - 减小阻塞窗口,但仍有数据不一致风险
    - 实际工程少用
- **柔性事务(BASE 思路)**
  - **TCC(Try-Confirm-Cancel)**
    - **Try**:预留资源(冻结余额、锁定库存)
    - **Confirm**:正式提交,使预留生效
    - **Cancel**:释放预留
    - **优点**:无长锁,各服务自治
    - **缺点**:每个业务方法要写三套接口、空回滚 / 悬挂 / 幂等都得处理
    - 框架:Seata-TCC、ByteTCC
  - **Saga**
    - 长事务拆成一系列本地子事务 + 每个子事务的补偿动作
    - 编排式(Orchestrator):中央协调器调度
    - 协同式(Choreography):各服务订阅事件触发
    - **优点**:无锁、扩展好,适合长流程(订单 → 库存 → 物流)
    - **缺点**:补偿设计复杂、隔离性弱(中间状态外部可见)
    - 框架:Seata-Saga、Cadence、Temporal
  - **本地消息表 / Outbox 模式**
    - 业务和"待发送消息"在同一本地事务,保证不丢
    - 后台扫描消息表 → 投递 [[消息队列]]
    - 消费者幂等消费,失败重试
    - **优点**:简单、可靠
    - **缺点**:消息延迟、需消费者幂等
  - **事务消息**(RocketMQ 半消息)
    - 1. Producer 发"半消息"到 MQ,MQ 暂不投递
    - 2. Producer 执行本地事务
    - 3. 成功则 Commit MQ 投递,失败则 Rollback
    - 4. MQ 定时回查 Producer 状态防丢
- **方案选型**

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|---|---|---|---|---|
| 2PC/XA | 强 | 低 | 中 | 跨库 CP 场景、银行 |
| TCC | 最终 | 中 | 高 | 资源预留型、电商支付 |
| Saga | 最终 | 高 | 中 | 长流程业务、订单链路 |
| 本地消息表 | 最终 | 高 | 低 | 异步通知、跨服务数据同步 |
| 事务消息 | 最终 | 高 | 中 | 配合 MQ 的消息驱动 |

- **共同要求**
  - **幂等性**:见 [[幂等性]],重试不重复执行
  - **超时与重试**:网络抖动是常态
  - **对账与补偿**:定时任务扫描不一致状态
  - **事务日志 / Outbox 表**:可追溯
- **避免分布式事务**
  - 设计聚合根:把强一致需求收敛在单库单服务
  - 业务降级:用最终一致 + 人工对账,可避免大部分场景
  - 异步通知 + 幂等消费 + 重试是性价比最高的"伪事务"
- **分布式数据库的内置事务**
  - Spanner / TiDB / CockroachDB / YugabyteDB 内部用 Percolator / Calvin 等协议提供分布式 ACID
  - 应用看到的还是单机事务接口

## 和其他概念的关系

分布式事务是 [[ACID事务]] 在分布式场景的延伸,触及 [[CAP定理]] 的核心权衡。强一致路径(2PC/XA)是 CP,柔性路径(TCC/Saga)走 [[BASE理论]] 最终一致。

依赖 [[消息队列]] 实现可靠异步通信,依赖 [[幂等性]] 保证消费正确,依赖 [[分布式锁]] 防止协调冲突。

[[微服务]] 几乎必然遇到分布式事务,设计原则是"能避免就避免",通过聚合根边界 + 异步事件最大化降本。

[[关系型数据库]] 的 XA 是 2PC 的具体实现;[[NoSQL数据库]] 多数无内置分布式事务,要靠应用层。

NewSQL([[分库分表]] 的演进)用 Percolator/Calvin 把分布式事务下沉到数据库层,大幅简化业务。
