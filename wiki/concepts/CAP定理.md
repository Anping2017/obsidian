# CAP 定理

## 定义

**CAP 定理(CAP Theorem)** 由 Eric Brewer 在 2000 年提出、Gilbert 和 Lynch 2002 年形式化证明:在一个分布式系统中,**一致性(Consistency)、可用性(Availability)、分区容忍性(Partition Tolerance)** 三者不可兼得,网络分区发生时,系统只能在 C 和 A 之间二选一。是分布式数据库设计与选型的核心理论。

## 核心要点

- **三要素定义**
  - **一致性 C**:所有节点同一时刻看到相同数据(线性一致性,Linearizability)
  - **可用性 A**:每个非故障节点都能在合理时间内返回响应(不阻塞、不超时)
  - **分区容忍 P**:节点间网络故障时系统仍能运行
- **常见误解澄清**
  - 不是"三选二",**P 在分布式系统中不可避免**(网络一定会分区),所以本质是"分区时选 C 还是 A"
  - 不分区时,系统**可以同时强一致 + 高可用**
  - "一致性"在 CAP 中特指线性一致,与 [[ACID事务]] 中的 C(完整性约束)不同
- **CP 系统(分区时保 C 弃 A)**
  - 分区时拒绝服务以保证读到最新数据
  - 例:ZooKeeper、etcd、HBase、MongoDB(默认)、TiDB、Spanner
  - 适合金融、配置管理等强一致场景
- **AP 系统(分区时保 A 弃 C)**
  - 分区时仍提供服务,可能读到旧数据,事后修复
  - 例:Cassandra、DynamoDB、CouchDB、Riak、Eureka
  - 适合社交、电商商品页等可容忍短暂不一致的场景
- **PACELC 扩展(Daniel Abadi 2010)**
  - 不分区时,在 **延迟 L** 和 **一致性 C** 间也有权衡
  - 完整描述:If Partition → A or C; Else → L or C
  - **PA/EL**:Cassandra、Riak、DynamoDB(分区可用 + 平时低延迟)
  - **PC/EC**:Spanner、HBase、传统单机 RDBMS(分区一致 + 平时一致)
  - 比 CAP 更精细
- **现实世界 CAP 选择**
  - **DNS**:AP,各地解析可能滞后
  - **数据库主从复制**:异步是 AP、同步是 CP
  - **Spanner**:号称"打破 CAP",实际是"分区时不可用 < 5 秒"的 CP,通过 GPS + 原子钟降低不可用时间
  - **Quorum 协议**(R + W > N):见 [[Quorum]],动态在 C 和 A 间调
- **应用层影响**
  - **AP 系统的应用**:必须接受最终一致,设计幂等、事件去重、读自身写补偿
  - **CP 系统的应用**:必须设计降级、超时重试、双活灾备
- **CAP 与一致性模型**
  - CAP 中的 C 是最强的线性一致,见 [[一致性模型]]
  - 实际多数分布式系统提供较弱一致性(最终一致、因果一致、读自己写)
- **后续发展**
  - Brewer 自己 2012 年发文澄清"3 选 2 是误读"
  - PACELC、FLP 不可能性、共识算法(Paxos / [[Raft共识算法]])是分布式理论的延伸

## 和其他概念的关系

CAP 是 [[一致性模型]] 的"最强一致性 vs 可用性"的简化框架,与 [[BASE理论]]("BASE 是 ACID 的反面,选择最终一致换取可用性")是分布式系统的两大权衡哲学。

[[ACID事务]] 在分布式中遇到 CAP 制约,催生 [[分布式事务]] 的 2PC/TCC/Saga 等折中方案。

[[关系型数据库]] 传统上 CP(强一致优先),[[NoSQL数据库]] 多数 AP(可用优先)。但 NewSQL(Spanner / TiDB / CockroachDB)用 [[Raft共识算法]] + 复杂工程做到"分区时短暂不可用、平时强一致 + 高可用"。

[[Quorum]] 协议(R+W>N)是在 CAP 中动态调节的实现机制。

[[微服务]] 设计离不开 CAP 思考:服务发现、配置中心、注册中心都是 CP 还是 AP 的选择(Zookeeper CP,Eureka AP)。
