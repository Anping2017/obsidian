# CQRS

## 定义

**命令查询职责分离(Command Query Responsibility Segregation,CQRS)** 由 Greg Young 在 Bertrand Meyer 的 CQS(命令查询分离)基础上扩展,提出**写模型(Command Model)** 和 **读模型(Query Model)** 在数据存储、对象模型、API 三个层面分离设计——写专注业务规则,读专注查询效率。

## 核心要点

- **核心区分**
  - **Command**:意图改变状态(`PlaceOrder`、`CancelSubscription`),通常无返回值,只关心成功/失败。
  - **Query**:不修改状态、返回数据;可在副本/缓存上跑。
- **典型架构**
  - **同步 CQRS**:Command 与 Query 共享数据库,但代码层分离。
  - **异步 CQRS + 投影**:Command 写到主库,事件流同步到独立的读模型(物化视图、ES、Redis),读端可水平扩展。
- **优势**
  - 读写分别优化——写模型可丰富复杂(聚合、不变量校验),读模型可扁平化便于查询。
  - 多种读模型:同一份数据可投影到全文搜索、报表、移动 API 不同视图。
  - 配合 [[事件溯源]] 自然——事件作为唯一真相源,读模型可重建。
- **代价**
  - 最终一致性:读延迟需用户体验设计配合。
  - 复杂度上升——两套模型、投影管道、版本演进。
  - 事件版本治理、幂等消费、重放、补偿都需要设计。
- **何时用**
  - 写复杂(领域规则厚)、读多样(多种视图)、读写规模差异大。
  - 不要在 CRUD 简单系统过早引入。

## 关系

- 与 [[DDD领域驱动设计]]:战术上 CQRS 让聚合专注写一致性,读用扁平 DTO,缓解领域模型同时服务读写的紧张。
- 与 [[事件溯源]] 是经典搭档——Event Store 是写模型,投影构造读模型。
- [[微服务]] 中,CQRS 常用于服务内部读写分离,事件用 [[消息队列]] 跨服务广播。
- 与 [[ACID事务]] 取舍——读端通常放弃强一致换扩展性。
- 是 [[六边形架构]] 端口划分的常见模式——Command/Query 端口分别接入。
