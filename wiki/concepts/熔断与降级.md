# 熔断与降级

## 定义

- **熔断(Circuit Breaker)**:在调用下游服务的故障率超阈值时,主动切断后续调用(快速失败),避免请求堆积引发雪崩。借鉴电路中的断路器模型,Michael Nygard《Release It!》提出。
- **降级(Fallback / Degradation)**:在系统压力大或依赖不可用时,有意简化或牺牲部分功能(返回默认值、关闭非核心模块、显示静态页),保证核心功能可用。

二者是 [[微服务]] 架构韧性(Resilience)的核心防御机制,与 [[限流]] 配合形成"自保三剑客"。

## 核心要点

- **熔断器三态**
  - **Closed(关闭)**:正常调用,统计失败率
  - **Open(打开)**:失败率超阈值,直接拒绝请求(快速失败),不再调用下游
  - **Half-Open(半开)**:Open 持续 N 秒后试探性放少量请求,成功则回 Closed,失败回 Open
- **触发条件**
  - **错误率**:近 1000 次调用中 50% 失败
  - **慢调用比例**:99% 调用 RT > 1s
  - **异常数**:连续 N 个异常
  - 多条件组合,Hystrix / Resilience4j / Sentinel 都支持
- **熔断器价值**
  - **防雪崩**:下游慢导致上游线程池耗尽,熔断切断这条传播链
  - **快速失败**:用户立刻看到错误而非长时间等待
  - **主动恢复**:Half-Open 自动探测,无需人工干预
- **降级策略**
  - **静默降级**:返回 null / 空集 / 默认值
  - **缓存降级**:返回上次成功的缓存数据(可能过期)
  - **简化逻辑**:跳过非核心步骤(如商品详情页跳过推荐模块)
  - **静态化**:大促时把详情页变静态 HTML
  - **关闭功能**:登录 / 下单等次要功能临时关闭
  - **限流即降级**:超额请求直接拒绝
- **降级触发场景**
  - **被动**:依赖故障、超时
  - **主动**:运维感知到系统压力,手动开降级开关
  - **预案**:大促 / 节日提前开启降级方案
- **典型实现**
  - **Hystrix(Netflix)**:开山之作,但 2018 年停止维护
  - **Resilience4j**:轻量级 Java 库,函数式编程,Hystrix 接班人
  - **Sentinel(阿里)**:中文社区主流,Java/Go/C++ 支持,集成限流+熔断+降级
  - **Polly**:.NET 生态
  - **Istio / Envoy**:服务网格层熔断,无侵入
- **熔断 vs 重试**
  - 熔断是宏观策略(整体故障切流量)
  - 重试是单次请求策略(瞬时失败再试)
  - 二者结合:重试 + 熔断,但要避免"重试风暴"加剧故障
- **熔断 vs 降级 vs 限流**
  - **限流**:控制流量进入,防自己被压垮
  - **熔断**:控制流量流出,防被下游拖垮
  - **降级**:故障时退而求其次,保命
  - 三者并行使用,层层防御
- **设计要点**
  - **快速恢复**:阈值不要过严,误熔断影响业务
  - **隔离单元**:按服务 / 接口 / 方法分别熔断,粒度细
  - **降级有备选**:不要降级返回错误,而是返回有意义的默认
  - **观测告警**:熔断打开必须告警,人工介入
  - **预演**:Chaos Engineering 主动注入故障验证熔断生效
- **常见坑**
  - **没设熔断**:一个慢服务拖垮全链路
  - **熔断阈值不合理**:把波动当故障熔断
  - **降级返回错误信息**:用户看到"系统繁忙"无任何价值
  - **未隔离线程池**:Hystrix 默认每依赖独立线程池就是为隔离

## 和其他概念的关系

熔断与降级是高可用架构的关键,与 [[限流]] 组成微服务韧性三件套,共同保护系统在压力 / 故障下的可用性。

部署在 [[API网关]] 与 [[服务网格]] 层,作为治理能力下沉,使应用代码无侵入。

[[微服务]] 调用链长,任一节点故障都可能传染,熔断降级是切断传染的核心手段。

[[消息队列]] 是另一个降级利器:同步调用降级为异步消息,削峰填谷。

[[幂等性]] 设计让重试 + 熔断的组合更安全:重试不会重复执行业务。
