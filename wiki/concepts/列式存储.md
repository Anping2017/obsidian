# 列式存储

## 定义

**列式存储(Columnar Storage)** 是将关系表的数据按"列"而不是按"行"在物理介质上连续存储的方式。每个列单独存储,使得分析查询(只读少量列、大量行)的 IO 与 CPU 效率远超传统行存。是 [[OLAP vs OLTP]] 中 OLAP、[[数据仓库]]、列存数据库(ClickHouse、Vertica、Druid、Parquet、ORC)的核心技术。

## 核心要点

- **行存 vs 列存**
  - **行存(Row Store)**:一行的所有列连续,适合按行读写整条记录(OLTP)
    - MySQL InnoDB、PostgreSQL Heap、Oracle、SQL Server
  - **列存(Columnar Store)**:同列的值连续,适合扫某几列的所有行(OLAP)
    - ClickHouse、Vertica、Greenplum、Snowflake
- **列存优势**
  - **IO 高效**:只读用到的列,SELECT a, b FROM t 不读 c d e
  - **压缩率高**:同列值类型一致、值域窄,适合 RLE、字典、Delta、ZSTD 等压缩
  - **向量化执行**:CPU SIMD 同时处理一列多行,远快于一行一行处理
  - **聚合极快**:SUM/AVG 只扫一列,带统计值跳块加速
- **列存劣势**
  - **写入慢**:一行写入要分散到多列,且需要更新多个文件
  - **行级更新差**:很多列存只允许追加 + 后台合并(类 [[LSM树]])
  - **点查询慢**:WHERE id=? 仍要查所有列拼回完整行
- **关键技术**
  - **列编码与压缩**
    - **RLE(Run-Length Encoding)**:连续相同值压成 (值, 次数)
    - **Dictionary Encoding**:字符串映射为整数
    - **Bit Packing**:小整数压到几位
    - **Delta Encoding**:差值编码,时间戳/有序整数特别有效
    - **ZSTD/Snappy/LZ4**:通用压缩封装
  - **谓词下推(Predicate Pushdown)**:WHERE 条件下推到 IO 层,跳过整块
  - **块统计(Min/Max/Bloom)**:每块存元信息,WHERE id=100 时跳过 min>100 的块
  - **向量化引擎**:批量处理(如一次处理 1024 行),发挥 CPU 缓存与 SIMD
- **典型实现**
  - **ClickHouse**:MergeTree 引擎 + 列存 + 向量化,极致 OLAP 速度
  - **Apache Parquet / ORC**:数据湖标准列存文件格式
  - **Druid / Pinot**:实时 OLAP,列存 + 倒排
  - **Vertica / Greenplum / Redshift**:商业 / 开源 MPP 数据仓库
  - **Snowflake**:云原生列存数据仓库
  - **DuckDB**:嵌入式 OLAP,列存 + 向量化
- **混合存储 HTAP**
  - 同库支持行存和列存,见 TiFlash(TiDB)、Aurora、HANA
  - OLTP 走行存,OLAP 自动同步到列存
- **列存与分区**
  - 通常按时间分区 + 分区内列存
  - 配合 [[分库分表]] 和分布式架构(Spark + Parquet on S3)做 PB 级分析

## 和其他概念的关系

列式存储是 [[数据仓库]] 与 [[OLAP vs OLTP]] 的物理实现支柱。它颠覆了传统 [[关系型数据库]] 的行存范式,但仍然支持 SQL 查询接口。

许多列存采用 [[LSM树]] 思想存储数据(写入到 MemTable、批量刷成不可变文件、后台合并),与 KV 数据库共享底层架构。

[[数据库索引]] 在列存中以"块统计 + Bloom 过滤器"形式呈现,跳过整块比传统索引粒度更粗但更高效。

[[查询优化器]] 在列存场景下需要新的代价模型(IO 按列、压缩比、向量化吞吐)。

数据湖(Data Lake)中 Parquet/ORC 列式文件 + Spark/Trino 查询,是 [[大数据]] 分析的事实标准。

[[OLAP vs OLTP]] 区分时,列存是 OLAP 的代表;HTAP 试图用一个系统兼容两种存储。
