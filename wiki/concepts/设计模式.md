# 设计模式 Design Patterns

## 定义

**设计模式(Design Pattern)**是软件设计中**可复用的解决方案模板**,针对反复出现的设计问题。它由 1994 年 Gang of Four(Erich Gamma 等四人,简称 GoF)在《设计模式:可复用面向对象软件的基础》一书中系统化,提出 **23 个经典模式**。

设计模式不是具体代码,是设计思想。它由四要素构成:
- **名称(Name)**:行业共通词汇,降低沟通成本
- **问题(Problem)**:何时使用
- **解决方案(Solution)**:类与对象的协作结构
- **效果(Consequences)**:权衡与代价

## 核心要点

### GoF 23 个模式分类

**创建型(Creational)**:关注对象创建过程
- 单例(Singleton)、工厂方法(Factory Method)、抽象工厂、建造者(Builder)、原型(Prototype)

**结构型(Structural)**:关注类与对象组合
- 适配器(Adapter)、桥接(Bridge)、组合(Composite)、装饰器(Decorator)、外观(Facade)、享元(Flyweight)、代理(Proxy)

**行为型(Behavioral)**:关注对象间职责分配与协作
- 责任链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者

### 高频模式速览

| 模式 | 一句话 | 应用例 |
|---|---|---|
| 单例 | 全局唯一实例 | 配置、日志、数据库连接池 |
| 工厂 | 由"工厂方法"统一创建对象 | Spring BeanFactory、Java URLConnection |
| 建造者 | 链式调用一步步构建复杂对象 | StringBuilder、Lombok @Builder |
| 适配器 | 把不兼容接口转成期望接口 | Java InputStreamReader |
| 装饰器 | 动态给对象加功能 | Java IO 流装饰、HTTP 中间件 |
| 代理 | 控制对真实对象的访问 | RPC 远程代理、AOP 动态代理 |
| 外观 | 提供统一简化接口 | API Gateway、Service Layer |
| 观察者 | 一对多通知 | 事件总线、MVC 视图更新、Pub/Sub |
| 策略 | 把算法族独立封装 | 排序比较器、限流策略 |
| 模板方法 | 父类定义骨架,子类填空 | Servlet HttpServlet、Spring JdbcTemplate |
| 责任链 | 处理请求依次传递 | Servlet Filter、Spring Interceptor、Netty Pipeline |
| 状态 | 行为随状态变化 | 订单状态机、TCP 状态机 |
| 命令 | 把请求封装为对象 | 撤销、Job/Task 队列 |
| 迭代器 | 顺序访问聚合对象 | for-each、Java Iterator |

### 反模式与常见误用

- **滥用单例**:成全局可变状态,测试和并发噩梦
- **过早抽象**:为了"以后可能扩展"建多层接口,反而难维护(YAGNI 原则)
- **模式即目的**:把模式名挂在嘴边,代码却没有真正问题
- **God Object**:违反单一职责
- **金锤子**:认识哪个模式就处处用

### 模式的 5 大[[设计原则SOLID]]

支撑模式背后的设计哲学:
- **S** Single Responsibility 单一职责
- **O** Open/Closed 对扩展开放、对修改关闭
- **L** Liskov Substitution 里氏替换
- **I** Interface Segregation 接口隔离
- **D** Dependency Inversion 依赖倒置

模式的核心价值在于实现这些原则。

### 现代化:动态语言与函数式视角

许多 GoF 模式在动态语言或[[函数式编程]]中"消失":
- **策略**= 高阶函数
- **命令**= 闭包
- **观察者**= 流(Stream)/响应式(Reactive)
- **装饰器**= 函数组合或 Python `@decorator`
- **迭代器**= 生成器

不是模式不重要,而是语言把它们内置化了。

## 和其他概念的关系

设计模式建立在[[面向对象编程]]四大特性(封装/继承/多态/抽象)之上,是 OOP 项目级别的"成语"。它与[[设计原则SOLID]]互为表里:原则是 why,模式是 how。

[[架构模式]]([[MVC架构]]、微服务、CQRS、事件溯源)是更大尺度的"模式",可视为多个 GoF 模式的组合。框架即"反向使用模式":Spring、Django、React 内部大量使用工厂、观察者、装饰器、策略,但用户通过框架享受这些模式而不必显式实现。

代码重构(Martin Fowler)的目标常常是"把代码逐步演化到某个模式",二者紧密相关。
