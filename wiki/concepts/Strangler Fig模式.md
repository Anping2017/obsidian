# Strangler Fig 模式

## 定义

**Strangler Fig 模式** 由 Martin Fowler 在 2004 年的 Bliki 文章中命名,灵感来自澳洲热带雨林的"绞杀榕"——这种植物的种子在老树上发芽,根逐步缠绕宿主、最终绞死老树并占据其位置。

在软件工程中,它指:**遗留系统不一刀切重写,而是在外围部署新组件,逐步把老功能迁移到新系统,流量按部分切换,最终老系统被完全"绞杀"替换**。

它是大型 Legacy System 改造的主流方法,避开了"大爆炸式重写(Big Bang Rewrite)"的灾难性风险。

## 为什么不直接重写

历史上"全面重写"项目失败率高:
- Netscape 6 重写导致市场份额崩盘(《Things You Should Never Do, Part 1》Joel Spolsky 2000)
- Borland → 失误重写 dBase
- Microsoft Vista 大幅延期
- 各种内部系统重写"工期 6 个月,实际 4 年"

**根本问题**

- 老系统含 N 年隐藏知识,文档不足
- 业务边界模糊,重写时容易缺失角落
- 重写期间业务持续变化,目标移动
- 团队疲劳、用户抱怨"啥时候上线"
- 商业风险(老业务出 bug 谁来修?)

## 工作流程

**1. 部署绞杀者(Façade)**

在老系统前加一层路由代理(API Gateway / 反向代理):

```
原: 客户端 → 老系统
新: 客户端 → 绞杀者代理 → (老系统 或 新系统)
```

代理初期 100% 转发到老系统,客户端无感知。

**2. 切片新功能**

按业务模块或端点切:
- 第一刀:用户认证模块(简单、独立)
- 第二刀:产品搜索(读多)
- 第三刀:订单创建(复杂、有事务)

新功能用现代技术栈实现,部署独立服务。

**3. 路由切换**

绞杀者代理按规则把请求分流:

```python
def route(request):
    if request.path.startswith("/api/users"):
        return new_auth_service(request)  # 新
    elif request.path.startswith("/api/search"):
        return new_search_service(request)  # 新
    else:
        return legacy_system(request)  # 老
```

可选:用 Header 或 Cookie 让 1% 用户走新版灰度([[灰度发布与蓝绿部署]])。

**4. 数据迁移**

新老系统可能用不同存储:
- **同读旧库**:新服务读老数据库(过渡期)
- **双写**:写入时写老库 + 新库(数据双备份)
- **CDC 同步**:Debezium 把老库变更实时同步到新库
- **断开旧依赖**:新功能逐步只读新库

**5. 模块逐一迁移**

按以上四步迭代,每个模块独立完成迁移、测试、验证。

**6. 老系统最终淘汰**

所有模块迁完后,老系统不再有流量,正式下线。

## 经典案例

**Amazon(2000s)**

从单体 OBIDOS 系统迁到微服务,经历近十年。每个团队("两个披萨团队")负责一项业务,逐步把功能从老系统切出。

**eBay**

从 Perl 单体迁到 Java,后又改 Scala。Strangler 风渐进迁移,从未"停摆"。

**许多银行核心系统**

COBOL 大型机系统迁现代云,有的 10-20 年还没完全完成。

**Shopify**

把单体 Rails 应用按业务边界拆为"Component-based monolith",再逐步独立部署。

## 与"全部重写"对比

| 维度 | Strangler Fig | Big Bang Rewrite |
|---|---|---|
| 风险 | 低(增量) | 极高(All or Nothing) |
| 工期 | 长(年单位) | 计划短,常拖延 |
| 用户影响 | 渐进、可控 | 上线日重大风险 |
| 业务并行 | 是 | 否(可能冻结需求) |
| 学习曲线 | 平缓 | 陡(全员压力) |
| 回滚 | 模块级回滚 | 几乎不可能 |

实践中 Strangler 几乎是大型系统重构唯一明智方案。

## 关键技术

**1. API 网关 / 反向代理**

- Nginx、Envoy、Kong、HAProxy
- 智能路由分发请求
- 渐进灰度(1% → 10% → 50% → 100%)

**2. 防腐层(Anti-Corruption Layer)**

新服务与老系统通信时,加一层适配:
- 老系统 SOAP / 老 API 转换为新 REST / GraphQL
- 数据格式映射
- 隐藏老系统怪异性
- 不让"老的味道"污染新代码

DDD 概念,Strangler 实践中关键。

**3. 双写 / 数据同步**

**双写代码**

```python
def update_user(user):
    new_db.update(user)
    try:
        legacy_db.update(adapt(user))
    except:
        log.error("legacy write failed")
        # 不阻塞主流程
```

**CDC**

用 Debezium / Maxwell 监听老库 binlog 同步到新库。

**4. Feature Flag**

LaunchDarkly、Flagsmith、Unleash:
- 不发布新代码
- 上线后切换 flag 开闭功能
- 异常时即刻关闭
- 与 Strangler 切换天然契合

**5. Contract Test**

新老系统接口契约测试,确保替换后行为一致:
- Pact、Spring Cloud Contract
- 验证请求 / 响应 schema、错误码、性能

## 实施挑战

**1. 数据一致性**

迁移期间新老两套数据,如何保证最终一致?
- 双写不可避免有竞争
- 用 outbox + CDC 异步化
- 审计任务定期对比

**2. 共享数据库**

老系统多个模块共享一个 DB,拆服务时数据库怎么拆?
- 阶段 1:多服务同 DB(只是代码拆)
- 阶段 2:逻辑分库(Schema 隔离)
- 阶段 3:物理分库(独立实例)
- 数据所有权按业务领域

**3. 跨模块事务**

老系统单体事务,新拆出来需 Saga 等模式:
- [[Saga模式]] 编排或协同
- [[Outbox模式]] 事件可靠投递
- 接受最终一致

**4. 接口兼容**

老 API 客户端可能内/外部都有,改不动:
- 防腐层把新服务包装成老 API
- 给老 API 加 Deprecation 头部,逐步驱赶客户端

**5. 团队节奏**

- 老系统团队继续维护
- 新系统团队加速
- 避免"我们" vs "他们"分裂

## 典型时间表

中等规模系统(50 万行代码):
- **第 1-3 个月**:技术栈选择、绞杀者代理上线、第一个简单模块
- **第 4-12 个月**:中等模块逐步迁移
- **第 13-24 个月**:核心交易模块迁移
- **第 25-36 个月**:数据完全切换、老系统下线

成熟团队 1-3 年,复杂金融核心系统 5-10 年。

## 反模式

**1. "永远在迁移"**

切到一半停滞,新老系统并存十年。需有明确"老系统下线截止日期"。

**2. 防腐层泄漏**

新代码大量引用老系统数据结构、命名,变成"穿新衣的老系统"。

**3. 双写不一致**

数据漂移积累,某天发现新老库差几万条记录,无法对账。

**4. 流量切换激进**

直接 100% 切新,出问题没办法。应灰度。

**5. 缺监控**

切换后没发现新版 P99 延迟翻倍,几小时后用户大量抱怨。

## 工程实践要点

- 从最简单、最独立的模块切入
- 每次切换 1% → 10% → 50% → 100%
- 异常监控、快速回滚机制
- 双写期数据每日审计
- 团队公开规划与进度
- 利益相关方(产品、运营)持续沟通

## 局限

- 工期长,需高管耐心
- 双系统并存,运维成本翻倍
- 难以应对老系统的破坏性变更
- 不适合彻底过时的技术栈(COBOL 找不到人)
- 不适合规模太小项目(直接重写更划算)

## 和其他概念的关系

Strangler Fig 是 [[微服务]] 转型、[[Clean Architecture]] 实践、[[DDD领域驱动设计]] 落地的核心方法论。它与 [[API网关]]、[[灰度发布与蓝绿部署]]、[[CI_CD流水线]] 等基础设施紧密配合。

防腐层概念来自 [[DDD领域驱动设计]],与 Strangler 互为表里——前者是边界设计,后者是迁移过程。Feature Flag 与 Strangler 切换粒度完全对应,二者结合是现代渐进式发布的事实标准。

它体现的"小步迭代、可观测、可回滚"哲学是 [[GitFlow与TrunkBased]] 中 Trunk-Based 开发、[[设计模式]] 中开放/封闭原则的延展——避免大规模一次性变化、拥抱增量演化。
