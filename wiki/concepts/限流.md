# 限流

## 定义

**限流(Rate Limiting)** 是控制单位时间内请求数量的技术,目的是保护后端系统不被突发流量或恶意攻击压垮。是高可用架构的基础防线,常部署在 [[API网关]]、[[负载均衡]]、应用层多处,与 [[熔断与降级]] 配合形成"流量自我保护"体系。

## 核心要点

- **限流的目标**
  - **保护下游**:防数据库 / 第三方 API 被打挂
  - **公平分配**:多租户场景按客户配额分配
  - **防 DDoS / 爬虫**:识别异常流量
  - **成本控制**:云服务按调用付费,限流防超预算
- **核心算法**
  - **计数器(Counter)**
    - 单位时间内累加请求数,超阈值拒绝
    - 简单但有"边界突刺":两窗口边界各到极限,实际 2 倍流量
  - **滑动窗口(Sliding Window)**
    - 把固定窗口拆成 N 个子窗口,滑动累计
    - 解决边界突刺,精度更高
  - **漏桶(Leaky Bucket)**
    - 请求进桶 → 桶以恒定速率漏出 → 桶满则拒绝
    - 输出**平滑稳定**,但不允许突发
    - 适合保护数据库等下游(下游怕抖动)
  - **令牌桶(Token Bucket)**
    - 桶以恒定速率加 token → 请求消耗 token,无 token 则限流
    - 桶有上限,**允许一定突发**
    - 适合保护服务自身(允许短期高峰)
    - Guava RateLimiter、Sentinel 默认
- **限流维度**
  - **全局**:整个服务的总 QPS
  - **单机**:每台服务器的 QPS,简单分布式不一致
  - **分布式**:多机协调统一计数(Redis + Lua)
  - **按用户/IP/API**:细粒度
  - **按租户/合约**:多租户 SaaS
- **分布式限流**
  - **Redis + Lua**:单 Redis 统一计数,保证原子性
  - **Sentinel**:阿里开源,集群限流模式
  - **令牌服务**:中心化发 token
  - **Envoy + Rate Limit Service**:服务网格统一限流
- **限流响应**
  - **拒绝**:返回 429 Too Many Requests + Retry-After
  - **排队**:把请求放队列等令牌(漏桶),客户端等待
  - **降级**:返回缓存 / 默认值,而非错误
  - **熔断**:连续超限触发熔断,见 [[熔断与降级]]
- **客户端 vs 服务端限流**
  - **服务端**:终极保险,所有客户端都要遵守
  - **客户端**:体感更好,快速失败不浪费网络;但恶意客户端会绕过
  - 实际两层都做
- **常见挑战**
  - **冷启动 / 流量预热**:服务刚启动 buffer pool / 缓存未热,需 slow start
  - **限流值难定**:压测得出基础值,根据 SLA 留余量(60%-70%)
  - **真实业务波峰**:不能一刀切,需弹性扩容 + 限流双重保险
  - **限流粒度**:粗粒度伤无辜,细粒度成本高
- **典型实现**
  - **API 网关层**:Kong/APISIX/Nginx limit_req
  - **应用层**:Sentinel、Guava RateLimiter、Resilience4j
  - **服务网格层**:Envoy Rate Limit、Istio
  - **分布式**:Redis-cell(Redis 模块)、Sentinel 集群
- **业务限流 vs 接口限流**
  - **接口限流**:按 URI / 方法 QPS
  - **业务限流**:按业务语义,如"单用户每分钟下单 ≤ 10"

## 和其他概念的关系

限流与 [[熔断与降级]] 是高可用三剑客的两个,通常组合使用:限流防自己被压垮,熔断防被下游拖垮。

部署位置常在 [[API网关]]、[[负载均衡]]、[[服务网格]] 上,统一治理外部和内部流量。

依赖 [[缓存]]([[Hash表]] / Redis)做高性能计数。分布式限流的精确性触及 [[一致性模型]] 与 [[CAP定理]] 的取舍。

[[Web安全]] 中,限流是防 DDoS / 暴力破解 / 爬虫的基础手段。

[[微服务]] 架构中,每服务都需限流自保,大流量场景结合 [[消息队列]] 削峰。
