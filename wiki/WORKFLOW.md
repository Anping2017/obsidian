# Wiki 工作流操作手册(SOP)

> **目的**:把 `raw/` 原始素材规范化提炼为 `wiki/` 概念知识库的标准操作流程。
> **适用**:每次处理 raw 文件(增量更新、批量补漏、新增域)都必须先读本文件。
> **先读**:`SCHEMA.md`(根目录,文件格式规范)、`wiki/INDEX.md`(已有词条速览)。

---

## 一、核心原则

### 1.1 三层信息流

```
raw/  →  wiki/  →  output/
原始     精炼      产出
```

- `raw/`:输入层,原始文档不做修改
- `wiki/`:知识层,SCHEMA 规范的结构化条目
- `output/`:输出层,基于 wiki 的产出(暂未启用)

### 1.2 文件类型与目录

| 类型 | 目录 | 用途 |
|---|---|---|
| `concept` | `wiki/concepts/` | 单一概念条目(理论/方法/工具) |
| `topic` | `wiki/topics/` | 综述/跨域主题/学派概览 |
| `entity` | `wiki/entities/` | 人物/组织/具体公司 |

### 1.3 命名规范

- **中文文件名优先**(SCHEMA 现行版允许中英混合)
- 技术术语保留英文(如 `RAG.md`、`Transformer.md`、`Spring Boot.md`)
- 多词中文用自然连接(如 `投资组合理论.md`)
- 多词英文用连字符(如 `react-hooks.md`)
- **不带空格的 wikilinks 目标**(避免别名歧义)

### 1.4 frontmatter 必需 7 字段

```yaml
---
title: 文章标题
type: concept | topic | entity
tags: [domain, status, ...]
sources: [raw/路径1.md, raw/路径2.md]
created: YYYY-MM-DD
updated: YYYY-MM-DD
summary: 一句话摘要(30-80 字)
---
```

### 1.5 文章结构(严格遵守)

**概念页**:
```
## 定义
## 核心要点
## 和其他概念的关系  (大量 `[[wikilink]]`)
## 参考源
```

**主题页**:
```
## 概述
## 多角度分析
## 结论
## 参考源
```

**实体页**(人物/组织):
```
## 简介
## 关键贡献
## 相关概念  (与之关联的核心概念)
## 参考源
```

### 1.6 wikilinks 规则

- 用简洁形式 `[[中文名]]`,不带路径,不带 `|alias`
- 第一次提到某概念时加 wikilink(同篇内重复出现可不加)
- 提到的概念若 wiki 中没有 → **不能创建空指向**,要么:
  - 创建一个 stub 文件
  - 改用普通文本(不加 [[]])

## 二、内容边界(关键)

### 2.1 ✅ 应当 wiki 化(写)

- **理论 / 概念 / 模型 / 方法**:有明确定义、可被引用
- **专业术语**:学科核心词汇
- **历史人物 / 知名机构**:对学科有贡献
- **学派 / 流派 / 框架**:思想体系
- **跨域综述**:连接多学科的整合主题
- **行业前沿**:技术演进、监管动态

### 2.2 ❌ 严格跳过(不写)

| 类别 | 路径/文件名特征 |
|---|---|
| **案例分析** | `案例` `case` `*-案例.md` |
| **模板** | `模板` `template` `表单` `表格` |
| **练习题** | `练习` `习题` `测试` `计算练习` `模拟交易` |
| **学习指南** | `学习指南` `学习路径` `导航` `检查点` `进度追踪` |
| **思维导图** | `思维导图` `知识图谱` `概览图` |
| **操作教程** | `如何` `操作步骤` `配置` `教程` `安装` |
| **销售话术** | `话术` `应对` `异议处理` |
| **清单** | `checklist` `100问` `100个` `清单` `cheatsheet` |
| **版本说明** | `更新日志` `changelog` `版本` `release` |
| **个人记录** | `读后感` `学习心得` `反思` `计划` `总结` |
| **空文件** | 0 字节 |

### 2.3 ⚠️ 模糊边界(看具体内容)

- **资源汇总**:链接清单 → 跳过;但精选+评论 → 可作 topic
- **代码片段**:具体实现 → 跳过;但范式/模式 → 可作 concept
- **实战经验**:个人故事 → 跳过;但提炼成方法论 → 可作 topic
- **行业案例**:单一案例 → 跳过;但成多案例对比综述 → 可作 topic

## 三、Agent 派发规范

### 3.1 派发原则

1. **域不重叠**:每个 agent 限定明确的 raw 子目录,互不冲突
2. **不修改既有**:agent 只能 Write 新文件,不能 Edit 现有 wiki(除非明确指定)
3. **必须先核对 INDEX**:agent 第一步读 INDEX 避免重复
4. **后台模式**:`run_in_background: true` 异步并发
5. **报告闭环**:每个 agent 完成后必须返回结构化报告

### 3.2 标准 Agent Prompt 模板

```markdown
**Vault**: D:\BaiduNetdiskWorkspace\Obsidian Vault
**先读**: SCHEMA.md、wiki/WORKFLOW.md(本文件)、wiki/INDEX.md(避免重复)

**目标域**: raw/{domain}/(N 文件)

**任务**: 写 X-Y 篇新 wiki 到 wiki/concepts/ 或 wiki/topics/(中文文件名)

**重点方向**: 
[列出 5-10 个具体子主题]

**已有(不重复)**:
[列举 INDEX 中相关已有词条名]

**写作规范**: 严格遵守 wiki/WORKFLOW.md
- frontmatter 7 字段全填
- 概念页:定义→核心要点→和其他概念的关系→参考源
- 每篇 50-100 行
- 大量 `[[wikilink]]` 互联

**绝对禁止**:
- 不修改现有 wiki
- 不重复(认真核对 INDEX)
- 不写案例/模板/练习/操作教程

**完成后报告**:
- 文件清单(按子主题分组)
- 跨域 wikilinks 关键节点
- 跳过项及原因
```

### 3.3 Agent 数量与时长

| 任务类型 | 推荐 agent 数 | 单 agent 产出 |
|---|---|---|
| 全域首轮 | 8-10 个 | 30-50 篇 |
| 单域深挖 | 1-3 个 | 25-50 篇 |
| 反查/修复 | 1-2 个 | 通常不写新文件,只修缺陷 |
| INDEX 重写 | 1 个 | 重写整个 INDEX.md |
| 增量(周维护) | 1-2 个 | 5-15 篇 |

## 四、反查与质量保证

### 4.1 反查项目清单

每次大批量 wiki 写入后,跑以下反查:

#### A. 孤立 wikilinks(orphan)
扫所有 [[xxx]] 检查目标文件是否存在。

#### B. 空格别名笔误
形如 `[[A 系列芯片]]` vs 文件 `A系列芯片.md`。

#### C. frontmatter 完整性
全 1600+ 文件检查 7 字段齐全。

#### D. type/目录一致性
type=concept 必须在 concepts/,以此类推。

#### E. 文章结构合规
按 type 检查必备四节是否齐全。

#### F. 重复检测
不同目录或不同变体名的同概念检测。

#### G. 跨域桥接缺失
关键学科对之间的 wikilinks 应密集。

#### H. Topic 中人物的 Entity 覆盖(2026-05-11 新增)
当一篇 topic 提到多个人物(如《西方哲学史脉络》《东方哲学》),应**每个人物都有独立 entity 页**。检查方式:
1. grep topic 文章里的人物名(包括纯文本和已有 wikilinks)
2. 对每个人名 ls 检查 wiki/entities/$人名.md 是否存在
3. 缺失 → 创建 entity(实体页结构:简介→关键贡献→相关概念→参考源)
4. 创建后回头把 topic 中的纯文本人名改为 `[[人名]]` 链接

适用范围:任何"X 史"、"X 流派概览"、"X 派别比较"等 topic。

### 4.2 反查脚本(Python 模板)

见 `wiki/scripts/`(待建)。两个核心脚本:

1. `scan_orphans.py` — 找孤立 wikilinks + 空格变体
2. `audit_quality.py` — frontmatter / 结构 / 重复检查

### 4.3 自动修复

可批量修的:
- ✅ 空格笔误 wikilinks(用 Python sed)
- ✅ 缺 sources 字段(写"待补")
- ✅ updated 字段过时(改为 today)

需人工决策的:
- ⚠️ 重复文件合并/重命名
- ⚠️ type 误标
- ⚠️ 命名不一致

## 五、增量更新流程(每周维护)

### 5.1 触发条件

- 每周一定时任务(见 `wiki/schedule.md`)
- 手动触发:用户说"处理 raw 最新改动"

### 5.2 增量流程

```
1. 找近 7 天 raw/ 修改的 .md 文件
   find raw -name "*.md" -mtime -7

2. 过滤掉 跳过类型(案例/模板/练习等)

3. 对剩余文件,按域分组

4. 派 1-2 个 agent 处理:
   - 检查每个文件的概念是否已在 wiki
   - 已存在 → 用 Edit 更新 sources 字段(加新 raw 路径)
   - 不存在 → Write 新 wiki 文件
   - 跳过类型 → 在报告中说明

5. agent 完成后 → 跑反查脚本

6. 更新 INDEX.md(增量追加新条目)

7. 更新 PROGRESS.md state

8. 可选:git commit
```

### 5.3 增量 Agent Prompt 模板

```markdown
**任务**: 处理近 7 天 raw/ 改动的增量

**先读**: SCHEMA.md / wiki/WORKFLOW.md / wiki/INDEX.md

**步骤**:
1. Bash: `find raw -name "*.md" -mtime -7 -newer wiki/PROGRESS.md`
2. 对每个文件:
   a. 跳过判断(看 WORKFLOW 边界规则)
   b. 概念查重(看 INDEX)
   c. 已有 → Edit sources;新 → Write
3. 报告:
   - 处理了 N 个 raw 文件
   - 新增 X 篇 wiki
   - 更新 Y 篇 wiki 的 sources
   - 跳过 Z 个文件 + 原因

**绝对禁止**:不修改 wiki 主体内容(除非概念过时);不删除任何 wiki。
```

## 七、git 工作流

### 7.1 何时 commit

- 每完成一个完整轮次(如一次大批量 wiki 写入)
- 每次反查修复后
- 增量更新后
- INDEX 重写后

### 7.2 commit message 模板

```
wiki: <动作> <数量> <主题>

例:
wiki: 新增 50 篇商业管理学概念
wiki: 修复 39 处空格别名 wikilinks
wiki: INDEX 终版重写 (1545 词条)
wiki: 增量处理近 7 天 raw 改动
```

### 7.3 不 commit 的内容

- `raw/` 通常已存在,不在本次工作范围
- 临时文件、Python 脚本输出

## 八、常见问题(FAQ)

### Q1:agent 写了重复的概念怎么办?
检查时发现 → 删除较短的、保留较完整的;两个版本都不错 → 合并或重命名其中一个为更精确的名字。

### Q2:某 raw 文件不属于任何已有学科怎么办?
判断核心概念,新建对应学科子节点;或归入"其他/未分类"。在 INDEX 反映。

### Q3:跨学科概念归到哪个 type?
- 概念主体属于哪个学科 → 该学科
- 综述类(如《金融与心理学》) → topic
- 跨学科理论(如博弈论) → 主域(经济学)

### Q4:stub 何时升级为 mature?
- 引用次数 ≥3 时主动升级
- 用户明确要求时
- 增量更新覆盖到时

### Q5:agent 可以修改既有 wiki 吗?
**默认不可**。例外:
- 反查任务明确要求修复 frontmatter
- 跨域桥接任务允许在"和其他概念的关系"段加 wikilinks
- 任何情况都不重写主体定义、不删除既有 wikilinks
